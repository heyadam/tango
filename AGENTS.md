# tango

A native macOS app for designing interactive interfaces: a patch graph in which every view is a patch, the patches that give the views behavior, and a live Viewer. The product spec is `tango-product-spec.md`; read it before adding features, and name the section a feature comes from.

This file is the guidance for every coding agent (Claude Code, Codex and others). Keep it here: `CLAUDE.md` only imports it (`@AGENTS.md`), so add nothing to `CLAUDE.md`.

## Build, test, run

```bash
swift test                      # all tests (Swift Testing); run after every change
xcodegen generate               # regenerate Tango.xcodeproj from project.yml (the project is gitignored)
xcodebuild -project Tango.xcodeproj -scheme Tango -configuration Debug -derivedDataPath build build
open build/Build/Products/Debug/Tango.app

# the iOS player, in the simulator (after touching anything it links: swift test never compiles its UIKit code)
xcodebuild -project Tango.xcodeproj -scheme TangoPlayer -destination 'platform=iOS Simulator,name=iPhone 17 Pro,OS=27.0' -derivedDataPath build build
scripts/player-shots.sh [gallery id…]   # its pictures beside the Mac's, in build/player-shots
```

Releases (a signed, notarized DMG on GitHub, from a `v*` tag) are `scripts/release.sh` and `.github/workflows/release.yml`; `RELEASING.md` has the steps and the signing setup. Hardened runtime is on in Release only, so a new device capability needs its entitlement in `project.yml`.

The app icon is `Icon/Tango.icon`, an Icon Composer file both apps build from (`ASSETCATALOG_COMPILER_APPICON_NAME: Tango`). It holds the full-bleed square artwork only: macOS and iOS cut the rounded shape, the margin, the shadow and the glass edge themselves, so never bake corners into `Assets/tango.png`. Edit it in Icon Composer (in Xcode's Applications), which also gives it dark and tinted looks.

Requires Xcode 27 / Swift 6.4 / macOS 27 (the iPhone player iOS 27), and `brew install xcodegen`. The assistant also needs Node.js 18 or later at run time; nothing else does.

`papertool` drives the same code without showing a window:

```bash
swift run papertool examples Examples              # rewrite the example documents from code
swift run papertool sample-video Sources/PaperEngine/Media/Sunset.mov   # the clip the Video Scrubbing pattern plays
swift run papertool viewer <doc> out.png [--tap x,y] [--seconds t]
swift run papertool record <doc> out.mov [--tap x,y] [--seconds t] [--no-touches] [--replay '<interact_prototype steps as JSON>']
swift run papertool editor <doc> out.png [--canvas] [--select-layer name] [--shader-code] [--assistant "<request>" [--chat "<earlier chat>"] [--attach file,…] [--queue "<request>"]]
swift run papertool json <doc>
swift run papertool reference                       # what agents are told: every view property, patch and port id, component, icon set
swift run papertool link <doc> [--port n] [--edit "<text>"]   # send a document to a player on this Mac (the simulator), as Play on iPhone does
swift run papertool glassfit build/reference/shots blur=24:3 detail=0.3:0.04 …   # fit the glass shader to iOS 26's (after Reference/run.sh glass-checker glass-stripes glass-circle)
swift run papertool assistant <doc> "<request>" [--out result.tango] [--model fable|opus|sonnet|haiku|openai:<id>|gemini:<id>|local:<id>] [--base-url http://localhost:8000/v1] [--no-pictures] [--effort low|medium|high|xhigh|max] [--attach picture-or-video,…]
swift run papertool extension new <name> [folder] | validate <folder> | install <folder> | list | uninstall <id>
swift run papertool extension export-component <doc> <component> <folder> | window out.png [--select id] [--review folder]
```

Every command takes `--extensions <folder>`, which keeps installed extensions there instead of in the app's own folder. Use it whenever you install one to try something: without it `extension install` changes what the person's app has.

`<doc>` is a `.tango` path, `empty`, or a gallery id (`Gallery.items`): `card`, `signin`, `search`, `people`, `live`, `controls`, `camera`, `sheet`, `list`, `header`, `swipe`, `pinch`, `hover`, `aurora`, `lens`, `carousels`, `photos`, `video`, `flow`, `morph`, `kit`, `chat`, `snow`, `stocks`.

## Layout

One Swift package, `TangoKit`, with a strict one-way dependency chain, wrapped by two thin app targets: `App/` (macOS, an `@main` around `EditorScene`) and `Player/` (iOS, an `@main` around `PlayerScene`).

```
PaperModel  <-  PaperEngine  <-  PaperRender  <-  PaperHost  <-  PaperEditor  <-  App      (macOS)
                                                             <-  PaperPlayer  <-  Player   (iOS)
PaperModel  <-  PaperLink        (PaperEditor sends with it, PaperPlayer receives)
```

- **PaperModel** — values and documents, no UI imports. `Value`/`PortType`, `Layer`/`LayerProperty`/`ViewType`/`ViewInput`, `Graph`/`PatchNode`/`Connection`/`GraphComment`, `ComponentDefinition`, `Document` (with `normalize` and the version 2 upgrade), `DocumentPackage` (the `.tango` package: `document.json` plus `assets/` and `extensions/`), `ExtensionManifest` and `PaperExtension` (an extension as its files).
- **PaperEngine** — runs a document. `PatchDefinition` + `StandardPatches`, `PatchRegistry`, `Runtime`, `ResolvedLayer` + `Layout`, `ComponentExpansion`, `ComponentLibrary` (`Library/`: the iOS shelf, its tokens in `SystemStyle`, and `ViewTemplate`), `Script` (JavaScript patches), `Icons`, `SVGPath`, `Fonts` and `MediaPatches` (icons, fonts and photos from outside: see "Icons, fonts and photos"; `Catalogs/` holds what ships of them), `ShaderSource` (reads a shader view's source; no Metal), `Samples` and `Patterns` (the example documents, built in code, and the `Gallery` catalog that lists them; `Media/` holds the one clip an example plays), `Extension` (`ExtensionSet`, what extensions add to the registry, `ExtensionLog`) and `Drawing` (`DrawCommand`, `ViewPainter`).
- **PaperRender** — `LayerRenderer`: a resolved layer tree to a `CALayer` tree. `ShaderCompiler` and `ShaderSurface` (`ShaderRenderer.swift`): Metal for shader views, the only GPU code. `DrawingRasterizer`: what an extension's view drew, as a picture. `VideoStills` and `VideoPlayer` (`VideoRenderer.swift`): AVFoundation for video views.
- **PaperHost** — what anything that hosts a running prototype does that is not a view, so it is written once: `PrototypeNetwork` (a Network Request patch's request as a `URLRequest`, the guarded session, sending), `PictureStore` (the pictures a prototype shows by name: assets decoded once, fetched and made ones kept, `ExtensionImages`), `VideoFiles`, `Viewport` (where a screen goes in the view that shows it), `WebAssets` (Material glyphs and Google fonts fetched and cached, and `WebAssetClient`, which hands them to a renderer), and `PrototypeHost`, which owns a `Runtime`, a `LayerRenderer` and all of those for a view that only forwards touches and frames (the player's; `ViewerView` is not on it yet). The Mac's Viewer and Canvas use the rest; a host service a second host needs moves here from `PaperEditor`, it is not copied. AppKit only behind `canImport`.
- **PaperLink** — the wire between the Mac and a phone: `LinkMessage`, `LinkFrame`, `LinkOutbox` and `LinkInbox`, `LinkKey`, and the sockets (`LinkTransport.swift`). It knows documents, never the engine. No default isolation.
- **PaperPlayer** — the iOS player (see "The device player"): `PlayerStore` and `PlayerLibrary` (portable, tested on the Mac), and `PlayerScene` and `PlayerView`, whose files are whole inside `#if os(iOS)`.
- **PaperEditor** — the app's UI. `DocumentStore` (+ `DocumentCommands`, `Clipboard`), `EditorView`, `CanvasView`, `PatchEditorView`, `ViewerView` + `ViewerWindow` + `ViewerSnapshot`, `InspectorView`, `LayerListView`, `GalleryView`, `DeviceServices`, `Recorder`, and the assistant (`AssistantToolbox`, `AssistantPrompt`, `AssistantSession`, `AssistantTransport`, `AssistantView`, `Assistant/sidecar.mjs`), the MCP server for outside agents (`AgentServer`, `AgentListener`, `OpenDocuments`, `AgentSettingsView`), and extensions (`ExtensionStore`, `ExtensionNetwork`, `KeyVault`, `ExtensionManagerView`).

`PaperRender`, `PaperHost`, `PaperPlayer`, `PaperEditor` and `papertool` use `defaultIsolation(MainActor.self)`. `PaperModel` and `PaperEngine` are isolation-free and must stay free of AppKit.

The package builds for macOS and iOS. Everything in `Sources/` compiles for macOS and is tested there; `PaperModel`, `PaperEngine`, `PaperRender`, `PaperHost`, `PaperLink` and `PaperPlayer` also compile for iOS, so AppKit and UIKit appear in them only behind `canImport`. `PaperEditor` and `papertool` never build for iOS: only the `TangoPlayer` scheme is built for it (the package's own schemes would try to build the editor).

## Views are patches

This is the model everything else follows from (spec 6.5).

- **A layer in code is a view in the interface.** The Swift types keep the name `Layer…` because a type called `View` would collide with SwiftUI's in every editor file. Everything a person or an agent sees says "view".
- **One object, shown in several places.** A view is one entry in the tree (`Layer`: nesting, order, stored values) plus exactly one graph node of kind `view` bound to it by `layerID`. The outline, the canvas, the Inspector and the patch all read and write the same stored values; the patch itself holds none (`node.inputs` stays empty, `node.name` unused).
- **`Document.normalize()` keeps that true**: one view patch per layer, none for a layer that is gone, the same inside every component. It runs on `Document.init`, on decode, and after every edit in `DocumentStore.changing`, so a new view gets its patch in the same undo step. It is idempotent. It also keeps every stored value as a file would read it back (`Layer.settleStoredValues`, `Document.settleStoredValues(of:)`): a number that is not finite is dropped, so the default applies (JSON cannot write one), and a container's one `padding` is split into horizontal and vertical, as decoding does. The runtime does not depend on it: a tree with no view patches just has no cables.
- **Ports.** `PatchRegistry.ports(for:)` gives a view node an input for every property any view can have, so it needs no layer. Which of them a view *shows* is the editor's business: `store.visiblePorts(for:)` = the chosen ones (`PatchNode.shownPorts`, nil = `ViewType.preset`) plus every cabled one. The Inspector's dot beside each input shows or hides its port (`store.setPort`).
- **x, y, width, height** are `ViewInput`s with a `part`: four number inputs over the stored `position` and `size`. `position` and `size` are ports too, shown only when cabled (old documents cable points into them). When both arrive, the number wins its half. `Runtime.apply(_:to:in:)` puts them together once per frame.
- **Stack, Grid and Scroll View are types, stored as a View with settings.** `Layer.type` (`ViewType`) is derived: a `view` whose `layout` is Stack is a stack, Grid a grid, a stack with `scrolls` a scroll view. `Layer.applicable` and `ViewType.preset` say what each shows; `Layer.new(_:)` makes one; `store.convert(_:to:)` ("Change To") is one property write, so cables and children survive. They are not stored kinds because a component's root is shown as the screen while it is edited (`Document.inside(of:)`), and must stay arrangeable.
- **A component instance's patch is its view patch** with `componentID` set (`PatchNode.isInstance`): its own view inputs, then the component's ports. `ComponentExpansion` keeps cables on view inputs on the expanded group and reroutes the component's ports inside. When the instance's patch and the root's patch inside drive the same input, the instance wins.
- **A scroll view's patch runs the scrolling** (`Role.view(…, scrolls: true)`): it has the outputs offset, velocity and dragging. Layout records each stack's `contentLength`; the runtime takes the range from it and hands the offset back as the internal property `contentOffset`, where layout starts its cursor. The old `scroll` patch still runs in documents that have one and is offered nowhere.
- **Every view's patch has frame outputs**: x, y, width and height as layout left them (`ViewOutput`, ids `frameX`, `frameY`, `frameWidth`, `frameHeight`, so one `shownPorts` list holds inputs and outputs). x and y are the position in the parent, what the x and y inputs set, so a stack's child reports where it was placed. They come after the scroll outputs (`PatchRegistry.frameOutputs`); on an instance they come before the component's outputs. Like inputs they show only when chosen or cabled (`store.shownOutputs`, `store.setOutputPort`; the Inspector's Frame Outputs section and the patch's Frame Outputs menu). The runtime fills them only for a view patch that cables or shows one (`CompiledNode.frameSlot`), from the last layout (`Runtime.laidOut`, one walk of the resolved tree after layout for every layer read), which is also where the View Size patch now reads: one frame late, so a view can feed its own inputs without a cycle, and a frame that did not change asks for no frame. A repeated view gives one row per copy. `settlePublished` keeps cables on them. Agents connect from them by id or name (`AssistantToolbox.outputs(of:)` offers them though hidden) and choose them in `set_ports` by id.
- **The graph is shown one view at a time**, like an app built one view controller at a time. A level (`Document.levelGraph(of:)`) is the patches of the views directly in a container, whatever is attached to those, and the patches kept there (`PatchNode.home`, nil = the screen; comments have a `home` too). A double-click on a view that can hold others steps into it (`store.open`), Command-Up or the back button above the outline steps out (`store.closeView`). The outline (`LayerSidebar`) shows the same level, one at a time: the views directly in the open view, with a header naming it and a back button when one is inside a view. Nothing expands in place. A view with views in it has a folder icon and a chevron that steps into it (`LayerRow.holdsViews`); rows reorder by dragging, but a view cannot be dragged into another container from the outline, and `store.openView` is where new views (`store.addView`) and patches (`addPatch`) go. A container's own patch is not in its level: it is one level out, among its siblings (only the screen's shows at the top, having nowhere else to be). Selecting a view in the outline opens the level its patch is in (`store.show` does the same for any patch). A cable may leave a level: the Patch Editor draws the end that is here as a dashed tail naming the other end. Levels are for the person only: the runtime and `ComponentExpansion` ignore `home`. `Document.settleHomes` puts patches in the level of the views they are cabled to; it runs for documents older than version 4, for the example builder, and for the patches an agent adds without `inside`. Deleting a view deletes what was kept in it; ungrouping moves it out.
- **A view publishes ports from inside it** (`PublishedPort`, kept in `PatchNode.published` on the containing view's patch): the port shows on that patch by name, one level out, and stands for `inner`, a port of a nested view's patch or of a patch kept in the view. It holds no value: `store.setLiteral` and `literal` follow it to the port inside (`Graph.resolved`). `ComponentExpansion` moves every cable on a published port to the real port before anything runs, so the runtime never sees one; a cable from outside wins over one the inner input has. `PatchRegistry.settlePublished` runs beside `normalize` after every edit: it drops a port whose inner port is gone or has left the view's level, keeps its type current, and removes cables left on ports a view's patch no longer has. Publish from the Patch Editor (right-click a port inside a view) or `store.publish`; the Inspector lists a view's published ports. The screen and a component's root publish nothing (a component has Input and Output patches). Grouping views carries what was published from them through the new group (the group publishes it, the port outside stands for the group's); ungrouping moves cables to the inner ports and points a port published further out at them. An input published outside always shows on the patch inside.
- **Version 2 documents** (property patches, component patches, `artboard`/`rectangle`/`group`/`oval`, `layout` Horizontal/Vertical, one `padding`) are upgraded on decode: `Document.upgradeToViews` and `Layer.init(from:)`. `Tests/Fixtures/v2` holds every example as it was saved then and how it played; `MigrationTests` checks both. (The playbacks of List and StickyHeader were recorded again when scroll views began to follow a finger from the slop: the same drag scrolls ten points less. A playback is recorded again only for a change to behavior that was meant, and the test says which.)

## How the engine works

- `Runtime.tick(dt:)` is deterministic and has no clock. Tests simulate frames with `advance(seconds:)`; a test that only waits for motion to end uses `settle(within:)`, which stops once nothing wants a frame (not for waiting out a delay that counts time, such as two taps a second apart). Tests run on the main actor one at a time, so a slow one slows the whole run: keep long waits out of `ViewerSnapshot` runs and pixel loops out of generic iterators (debug builds are slow there). The runtime does no I/O: the host performs network requests (`requestHandler` / `complete`) and device work (`setDevice`, `deviceEvent`, `takeEffects`), which is what lets tests fake them.
- A patch is a `PatchDefinition`: ports plus `evaluate(inout EvalContext)` over scalar values. A new patch should be about 20 lines in `StandardPatches`.
- **Loops are lifted by the runtime.** Outputs are stored as one row per loop index (`outputs[node][row][port]`); an ordinary patch runs once per index with its own state. Only patches made with `.wholeLoop` see whole loops.
- The Time patch asks for every frame while its Running input is on; off, it holds its time and the prototype can rest (the Activity Indicator stops it when it is not animating).
- A patch re-evaluates only when an input changed or it set `wantsNextFrame`. When nothing wants a frame, `needsAnotherFrame` is false and the Viewer pauses its display link. Idle CPU should be 0.
- **Network Request** (spec 7.6): GET, POST, PUT, PATCH, DELETE, with Headers and Query as text, one field per line (`Name: value`, `name=value`) or a JSON object; `NetworkRequest.forPatch` (pure, tested) builds the request. An answer whose `content-type` is `image/…` gives no JSON or text but an Image output, `NetworkRequest.pictureName(for:)` (`fetched:<id>`), which the Viewer keeps (`PictureStore`: the `mostKept` shown most recently; an answer labelled a picture that does not decode reaches the patch as text) and its `imageProvider` resolves, like the Camera's `capture:` photos. `PrototypeNetwork.urlRequest(for:url:)` drops the forbidden headers (`forbiddenHeaders`, which `ExtensionNetwork` goes by too) and any with a control character, and sends `Origin: null` to loopback (`guarded`), so a document cannot drive the app's own agent port; requests go through `PrototypeNetwork.session`, which applies `guarded` again on every redirect, since any server can answer 307 and send the POST on to 127.0.0.1. Query fields are appended to the address's own query as written, each strictly encoded. Not yet: multipart upload, video or sound answers.
- **AI patches** (not in the spec): Generate Text (`aiText`: Claude or OpenAI, chosen by the model's name, streamed, with a conversation, and a Stop that keeps what was written, and the question alone when nothing was), Generate Image (`aiImage`), Speak (`aiSpeech`) and Transcribe (`aiTranscribe`), category AI, in `AI.swift`. Like Network Request the runtime does no I/O: role `.ai(task)` runs `evaluateAI`, which hands an `AIRequest` (phases send, startRecording, stopRecording, cancel) to `aiHandler`; the host reports with `runtime.update(ai:_:)` (`partial`, `recording`, `playing`, `finished`, `failed`). A request the patch no longer waits on is forgotten; `restart()`, and deleting or replacing the patch (`compile`), cancel what is in flight. `AIService.waiting` holds requests waiting on the person (the key question, the microphone prompt), so a cancel or a let-go Record reaches them before anything is sent or recorded, and one key question answers every request that waits on it. When the Viewer is hidden, `AIService.quiet` ends speech and recording as if they had finished (not a recording still waiting on a prompt, which can itself hide the Viewer), and speech that arrives while hidden is not played. Transcribe keeps a let-go recording being transcribed (`AIState.transcribing`) while a new one records. Nothing sends without a Send pulse, so opening a document costs nothing. The host is `AIService` (PaperEditor), one per Viewer: it builds each provider's request (`textRequest`, `imageRequest`, `speechRequest`, `transcriptionRequest`, tested as plain functions), reads streams (`AIStream`), plays speech, records the microphone, and keeps made pictures under `ai:<id>` with fetched ones. Keys are `AIKeys`: the keychain (`KeychainVault.aiService`), with the last four characters in the defaults so Settings never opens the keychain to list them; the Settings window's AI section enters them. The first use of a provider's key in a Viewer asks the person (`ask`, an alert; Settings can turn it off), so a shared prototype cannot spend someone's credit unasked. Pictures and the assistant's hidden runs never call (`sendsRequests` false). Model ids live in `AIRequest.textModels` and its neighbors; update them when providers ship new ones (OpenAI's speech models shut down 6 January 2027, with no `/v1/audio/speech` replacement named yet).
- **Apple's models** (not in the spec): `AIProvider.apple`, chosen by a model name starting `apple` (`AIRequest.onDevice`, "apple-on-device"), runs on the device that plays the prototype with no key, no question and no cost: Foundation Models for Generate Text (streamed, with its conversation as a `Transcript`, a picture as an `Attachment`; pictures of earlier turns are not shown again), the system's voices (`AVSpeechSynthesizer`) for Speak, SpeechAnalyzer for Transcribe (the Mac records as before and hands the file over). Two patches run only on it: **Generate Object** (`aiObject`, task `object`), guided generation into the fields listed one a line in Fields (`AIField.parse`, pure and tested: `name: kind - what it is`, kinds text, number, whole, yes/no, list, `list of 3 number`, `a | b` choices), which become a `DynamicGenerationSchema` and stream as JSON (`.partial` carries the JSON so far); and **Translate** (`aiTranslate`, task `translation`), the Translation framework between installed languages, `NLLanguageRecognizer` for From Detect, languages by name or code (`AIRequest.languageCode`). The host is `AppleIntelligence` (PaperHost), so the Mac (`AIService.apple`, which skips `permitted` for it) and the iPhone player (`PrototypeHost.apple`) run the same code; the player runs only these (a cloud model fails with `PrototypeHost.noAI`, Transcribe with `noRecording`). Settings' AI pane says whether the model is ready (`AppleIntelligence.status`). Programmatic image making is gone in 27 (`ImageCreator` stops working), so there is no Apple image model; Private Cloud Compute is not offered (it is for App Store apps, and refused this Mac's tools). `AppleIntelligenceTests` runs the real model when this Mac has it on, about a second each, and skips otherwise. The gallery's `chat` (On-Device Chat) shows it off, built the way ChatGPT's is: suggestion cards, typed words, or words said into a held microphone (Transcribe on apple-on-device) go to Generate Text with Remember on; the round button talks while the field is empty, sends once there are words and stops an answer being written (Generate Text's Stop, which keeps what was written as the answer); each finished answer has a row of actions (copy, thumbs, read aloud with Speak on apple-on-device). A script (Thread) keeps the newest messages that fit, oldest first, each with a key a new chat does not reuse, so the stack can sit at the bottom (a stack's End only applies while its content fits); a script (Feedback) keeps what was done to each message by that key, since a Loop Option Switch knows a row and rows shift as messages come and go; a script per message (Message Style) makes a bubble or plain words, sizes them and picks the action symbols; and a glow shader (Strength from a spring on Loading, Phase from a Time that runs only while loading) runs round the composer while it thinks, so it costs nothing at rest. Building it found four gaps in the engine, each now fixed and held by `EngineGapTests` (and `TextMeasurerTests`): see the bullets on rows, pulses, text fields and text measuring.
- Pulses last exactly one frame; the runtime clears them at the emitting patch's turn, after gathering that patch's own inputs, so a patch cabled to itself reads its pulse from the last frame as any back edge does. A patch with a pulse arriving is evaluated even when its inputs equal last frame's, so pulses in two frames running are two.
- Cycles are allowed; a back edge reads the previous frame.
- **Components are expanded, not interpreted.** `ComponentExpansion` replaces every instance with a private copy of the definition's layers and patches, with ids derived from the instance id, so the runtime only ever sees a flat tree and graph. A component's interface is its `component.input` / `component.output` patches.
- A view whose input receives a loop is repeated once per value; everything inside a repeated view repeats with it. Layout then arranges the copies. A copy whose `visible` is off is left out of the tree but keeps its row: the patches attached to a repeated view have one row per copy up to the last one there (`ResolvedLayer.instanceCounts`), so a tap on the copy after a hidden one is that copy's. The loop has to reach the view that should repeat as a whole: one that reaches only some of its children repeats those apart. Loop Select, Loop Count and Loop Builder take every type a loop can hold, JSON included (`StandardPatches.loopValue`).
- **Input is fed by the runtime, not by patches.** The host sends `InputEvent`s (`runtime.send`); `processEvents` hands touches to the gesture arena and keeps focus, keys and hover, once per tick; patches attached to a view (`interaction`, `tap`, `longPress`, `pan`, `swipe`, `pinch`, `rotation`, `hover`, `textInput`, `layerSize`, `videoTime`, and the retired `scroll`) only have port definitions and get a `Role` in `compile`. A new one needs: a definition in `StandardPatches.input`, a `Role` case, a branch in `compile` and in `tick`, an entry in `PatchGuide`, and its kind in `DocumentStore.touchPatchKinds` (which is what the editor, the patch library and the assistant go by) and in the outline's two Touch menus (`LayerListView`); a gesture also needs a `GestureArena.Kind` and a line in `touchTargets()`.
- **Touches have identities.** `touchBegan(id:)`, `touchChanged(id:)`, `touchEnded(id:)` and `touchCancelled(id:)` are fingers as a phone reports them, any number at once: a player forwards its `UITouch`es and nothing else. `touchDown`/`touchMoved`/`touchUp` are the same for finger 0, for a host with one. `pinchBegan`/`pinchChanged`/`pinchEnded` are an *indirect* pinch: one the host already recognized (the Mac trackpad's magnify and rotate, as iPadOS delivers a trackpad's), which drives the Pinch and Rotation patches of the view under it with no fingers and no thresholds. Points are made finite on the way in.
- **The gesture arena** (`GestureArena`, `Gestures.swift`: plain values, no views or patches, tested alone by `GestureArenaTests`) tells gestures apart as UIKit's recognizers do. For each finger that lands, `Runtime.touchBegan` says which recognizers it is offered to (`Candidate`, the node's index as `owner`): the topmost view under it that has any touch patch is its view (views without one do not block), and it goes to that view's gesture patches, to those of every view that view is in, and to the scroll views it is in, deepest first. The raw touch is offered separately, as a view's own touches are from its recognizers in UIKit: to the Interactions of the topmost view under the finger that has an Interaction or a Swipe, whatever gesture patches lie over it, so a picture that only listens for a pinch does not keep a tap from the button behind it or the container it is in. Recognizers are named by their patch's place in `nodes`, so `compile` renumbers them (`arena.renumberOwners`) when a document is edited with fingers down. A recognizer is `possible` until it begins or fails; each patch reads its `Reading` (`arena.reading(owner:hit:)`) in `tick`, one per repetition, and writes values only once its gesture has begun, so they keep their last reading after the fingers lift. The rules: the first to begin takes its touches from the rest, a deeper view being asked first; Pan, Pinch and Rotation on one view go together (UIKit wants a delegate for that; a prototype has none); a Tap waits for a Tap with more taps on the same view to fail, and only then; a Long Press that begins fails the taps and keeps a scroll view from beginning; a raw touch (`Kind.touch`, the Interaction patch) is no recognizer, never stops another, and is cancelled only by a scroll view or the host. **Nothing jumps when a gesture begins**: translation, scale and rotation count from where it left its slop (`GestureMetrics`: 10 points, 8 points of spread, 5 degrees), a pan follows the middle of its fingers and is re-based when one joins or lifts. Fingers that move in the same frame are looked at together (`arena.settle`, before any other event and before `advance`), or two fingers spreading would for an instant be one finger dragging. `arena.needsFrames` keeps the prototype running only while a tracked finger is down, a gesture is under way or a tap waits for another.
- **Text fields** (`LayerKind.textField`): a tap on one gives it focus, a tap elsewhere or Return takes it away. The runtime keeps what was typed per field (`fieldText`) and shows it by overriding the layer's `text`, unless a cable drives that property. Clear empties the field at once, but Text gives what was there for that one frame more, so a Clear cabled from the field's own Return (a cycle, which may be ordered either way) does not empty the words the same Return sends; the empty Text comes on the next frame with its Changed pulse, a frame the runtime asks for itself (`fieldsCleared`). `ResolvedLayer.isEditing` marks the focused field so the renderer draws a caret; the blink is a Core Animation animation, so an idle field costs no frames. There is no on-screen keyboard: typing comes from the Mac's keyboard (`ViewerView.type`) or from `.text` events.
- **Scroll views are recognizers too** (`Kind.scroll`, one per scroll view, owned by the first patch that scrolls it: `scrollOwners`). One begins once the finger has left `tapSlop`, and follows from there, not from where the finger came down; `evaluateScroll` reads how far its finger has gone since. When it begins it **cancels the touch of what is inside it**, as iOS does: an Interaction there goes Down off and neither taps nor long-presses, a Tap or Swipe fails, focus is not moved. Which one takes a touch is settled when the finger leaves the slop (`decideScroll`), at the innermost scroll view's turn, so what is inside it was asked first and what is around it was not: the innermost along the drag's main direction that can still move that way (`canScroll`), else the innermost along it; so carousels sit in a vertical page, and an inner list at its end hands the drag out. A drag *across* every scroll view under it is left to the content when the content has anything that could mean it (an Interaction, a Swipe, a Pan); with nothing there, the innermost scrolls anyway. A Pan with a Direction fails the other way, which is how a row that slides sideways shares a vertical list. A scroll view takes one finger: a second finger on a view that listens for two (Pinch, Rotation, a Pan that allows two) before it began fails it; one already scrolling keeps the touch and they never begin. A finger that lands on a scroll view still moving faster than `caughtScrollSpeed` catches it at once, and is not offered to what was passing under it. The `carousels` pattern, `NestedScrollViewTests` and `GesturePatchTests` hold this. A scroll view keeps one offset, so a carousel cannot be a repeated view: build each as its own view.
- **In the Viewer** the mouse is finger 0. Holding Option shows a second finger mirrored from the pointer through a pivot in the middle, as in the iOS Simulator; pressing puts both down as two touches (finger 1 is the mirror), and dragging spreads and turns them. Holding Shift as well moves the pivot with the pointer, before pressing (to put the fingers somewhere else) and while pressing (both travel together: a two-finger pan). Both fingers must be on a view for its Pinch to hear them. Trackpad magnify and rotate are the indirect pinch. A swipe is a touch that travelled `Runtime.swipeDistance` and was still moving at `swipeSpeed` when lifted. Hover comes from pointer movement, sent only when the prototype has a Hover patch (`runtime.usesHover`), so other prototypes stay idle under a moving pointer.
- Coordinates: points, origin at the parent's top-left, y down. `position` places the view's anchor (default top-left); scale and rotation pivot on the center.
- **Layout** (`Layout.swift`): a stack flows its children along `axis` with `spacing`, `paddingHorizontal`/`paddingVertical`, cross-axis `alignment` and `distribution` of the space they leave; a grid uses equal `columns`. A child is Fixed, Grow or Auto in each direction, and `absolute` opts it out. Layout overwrites the position of arranged children, so their x and y are shown dimmed (`store.isPlacedByParent`).

## Screens and flows

Not in the product spec. A prototype can have several screens, shown side by side on the Canvas, with flows between them that are patches.

- **A screen is a view with a setting**, like a stack: `Layer.page` (true, or absent) on a plain view directly in the root makes `Layer.isPage`. There is no second root and no new `ViewType` (a screen can still be a stack or hold a shader); the version is still 4. `Layer.settlePages`, run by `normalize`, drops the setting anywhere else, so it never survives inside a container or a component. A document with no screens has one, the root, exactly as before. The interface calls a page a Screen, and the root "Device" once it holds some. Icons: a screen is `screenSymbol` (a page with something on it), the Device a phone, a plain view an empty rectangle; Navigate and Navigate Back have their own (`patchSymbol`) rather than the State category's switch.
- **A screen fills the device.** The root's layout (`placePages` in `Layout.swift`) gives each page the root's size and puts it at the corner; a `position` that arrives as an override counts as an offset from there, which is how the runtime moves one. `store.isPlacedByParent` is true for a page, so its x and y are dimmed and the Canvas does not drag it; `Layer.preset` shows only Fill on its patch.
- **The runtime owns which screen shows** (`Navigation`, `Navigation.swift`: plain values, tested alone by `NavigationTests`, like `GestureArena`). It keeps a stack of screens, the first page to start with, and at most one `Move` (the screen that travels, the one under it, a style, how much of it is in place, stepped with `Spring.step`). Each tick, after the patches and before what cables bring (`apply`), `Runtime.tick` writes `visible` off for every screen that is not there and `position` or `opacity` for the two in a move into `overrides`: so a cable on a screen still wins, as with `contentOffset`. The screen that travels is drawn over the others (`ResolvedLayer.bringPageToFront`), under whatever is in the root after the screens, which floats over all of them. A hidden screen takes no touches; its patches still run. `restart()` goes back to the first screen; a screen that is deleted leaves the stack (`settle(pages:)` in `compile`). With no pages none of this runs.
- **Navigate** (`PatchKind.navigate`, category State) is attached by `layerID` to the screen it shows, so it sits at the top level beside that screen's patch; `DocumentStore.fits` lets it attach only to a screen. Go (pulse), Style (Push, Modal, Fade, Instant; `Style.named` also reads "Switch", its first name) and Response in; Progress, Arrived and Showing out. **Navigate Back** (`navigateBack`) pops: the screen on top leaves the way it came, and one still arriving turns round where it is. Instant changes at once and starts over on that screen, leaving nothing to go back to (tabs: choosing a tab from a pushed screen does not leave that screen to swipe back to). Roles `.navigate` and `.navigateBack`; an event (`Navigation.Event`) lasts through the frame after the one it happened in, which is when the patches pulse.
- **What floats over every screen, and what covers it**: views directly in the device (a tab bar) are drawn over the screens, and stay over a pushed screen; a screen presented with Modal is drawn over them too, as a sheet covers a tab bar on iPhone (`Navigation.coversEverything`, `ResolvedLayer.liftToTop`). A screen is opaque to touches: a finger on it never reaches what is behind it, though the screen itself listens for nothing (`touchBegan` cuts the hits at the first screen). On the Canvas an arrow from a view over every screen leaves from its copy on the screen beside the one it shows, and a view moved to another level has its patch put in free room there.
- **`DesignerWorkflowTests`** builds a tab bar app from an empty document the way a person does on the Canvas (draw, add screens from the slot, step in, Move To Every Screen, draw flows) and plays it: tabs, a push, a sheet over the tab bar, Back. It found the three rules above; add a walk-through there for a workflow a change affects. `TANGO_WORKFLOW_OUT=<folder>` keeps the document it builds, to look at with papertool.
- **Swipe back**: a finger that comes down within `Navigation.edgeWidth` of the left edge of a screen that was pushed drags it back as on iPhone (`Runtime.edgeSwipeTakes`, before the gesture arena: the edge is the system's, and nothing under the finger hears it). `Navigation.dragBack` follows the finger without touching the stack (`Move.dragging`); `endDragBack` goes back past half way or on a flick to the right, and otherwise slides home with no event (`Move.quiet`).
- **Morph** (`Style.morph`): both screens stay where they rest and the runtime blends them after layout (`ResolvedLayer.morph`, `Morph.swift`): a view with the same name on both screens (a name used once on each, not repeated) moves and resizes from its frame on the one to its frame on the other and blends `morphedProperties`; the arriving screen's fill and the views it does not share fade in, the leaving screen's fade out, and its matched views are hidden so each is drawn once. Limits: the frame is in the parent's coordinates (a scaled or turned container is not followed), and what is inside a matched view is laid out for its final size.
- **The Canvas marks the screen the Viewer is on** with a green "Viewer" pill on its title (`store.viewerScreen`, set in `frameDidTick` only when it changes, so it costs nothing per frame).
- **A flow is not stored.** `store.flows` reads them from the graph: every Navigate or Navigate Back, with the view its Go can be followed back to (the first patch upstream that is attached to a view). `store.addFlow(from:to:style:)` makes the usual one in one undo step: the view's Tap patch (the one it has, if any), a Navigate on the screen, and a cable; `to: nil` makes a Navigate Back kept in the view's level.
- **`store.addScreen()`**: the first time, everything the root held goes into a new first screen with the root's fill and arrangement, and the patches and comments kept at the top go with it (`home`), so nothing built is left outside a screen. `moveScreen`, `setScreen` (Make Screen / Make Plain View in the outline's context menu). Insert > Screen.
- **How screens read in the interface**: the first screen added renames the root "Device", and new screens are numbered by their place ("Screen 3"). `Layer.typeName` says Screen, Device or the view's type wherever a person reads it. A screen's Inspector has only Fill and Arrange Children (`Layer.applicable`: its frame is the device's), with a footer saying what a screen is; the Device's has the size of every screen and its fill. The outline lists the Device and what floats over the screens under Views, and the screens in their own Screens section in board order, dragged to reorder (`moveScreen`). Selecting the Device on the Canvas outlines every screen. The Canvas says what a press does in a tooltip (`help(for:)`).
- **Designer workflows** the editor supports directly: **Preview from Here** (a screen's right-click menu on the Canvas or in the outline) starts the Viewer on that screen with nothing to go back to (`store.preview(from:)` sets `store.previewScreen`, which the Viewer hands to `Runtime.startPage` on every restart; not saved, and an assistant's replay always starts on the first screen, as its hidden run did); **Move To** puts a view on another screen or over Every Screen, for a tab bar or a status bar (`screenMoves(for:)`, `move(_:toScreen:)`, only for a view directly on a screen or in the device, keeping its place); Command-2 zooms to the selection, or to its screen when it is small (`zoomToSelection`); adding a screen shows the Canvas, and a document with screens opens with it shown.
- **New views go into a screen, not over all of them.** At the top level of a document with screens `store.containerForNewViews` is the selected screen (or the one holding the selection), else the first; `addView`, `insertComponent` and a paste from elsewhere all go by it. What is directly in the root beside the screens floats over every screen (a tab bar); an agent puts something there with `parent: "screen"`. A copied screen is pasted as a screen.
- **The Canvas is a board** (`Board`, pure and tested by `BoardTests`): one frame per screen in a row, in document order, the first marked as the start. Nothing of it is stored. `CanvasView.resolve` resolves the document once with every screen there (`Runtime.showsEveryScreen` when components make it run a runtime), `CanvasView.trees` gives each frame the root with only its screen, and each frame has its own `LayerRenderer`. The picture is made again only when the document or the registry changed, not for a selection.
- **Editing on the Canvas** goes through the store's commands and follows the graph's levels: a click selects a view of the open view (or of the screen clicked on), a double-click or Return steps into a container and retypes a text in place, Escape steps out. A view its stack or grid places is dragged among its siblings and never given a position: it goes after every sibling whose middle the pointer has passed (`Snapping.place`), which stays put for rows of different sizes where "the sibling under the pointer" swapped them back and forth; a free view snaps to its siblings and its container (`Snapping.snap`, Command suspends it) with guide lines; a drag from empty room is a marquee; a view let go over another screen moves to it; a new view goes into the open view where it was drawn (`addLayer(into:)`). A screen's title selects it and drags it among the others; "+ Screen" adds one.
- **The Canvas says what a press would do before it is made.** `CanvasView.spot(board:cursor:)` is the one place that says what is at a point (`Spot`: the add-screen slot, a title, the flow handle, a resize handle, an arrow, the view a click selects, empty room on a screen, outside); `mouseDown`, the hover highlight, the cursor (`cursor(for:)`: a pointing hand on what is clicked, the system's resize cursors on handles, a crosshair with a drawing tool, an open hand with the space bar) and the right-click menu (`menu(for:)`) all go by it. Add a new thing to press as a `Spot` case, not as a branch in `mouseDown`.
- **How it looks**: each screen lies on the board as a sheet with a soft shadow (`paperLayer`, under the renderers) and a hairline edge; a dashed slot the height of a screen after the last one adds a screen; inside a view everything else is dimmed (`scrimLayer`, an even-odd hole round the open view); a view being dragged has a badge with its size while it is resized and its position while it moves (none at rest, so it never covers what is below; the Inspector says both); the screen a dragged view or a drawn arrow would land on is outlined. Colors are the system's (`updateLayer`), so it follows light and dark.
- **Everything the Canvas draws over the screens is on whole pixels.** `redraw` puts the board's corner on a pixel (`pixel(_:)`), so every screen starts on one; `sheetRect`, `outline(of:lineWidth:into:)` and `crisp(_:lineWidth:)` put boxes on pixel edges and move a line an odd number of pixels wide by half a pixel, so a hairline is one sharp pixel (`1 / pixelScale`) and a selection outline is not a blur. A turned view keeps its true corners. Labels are `CanvasPill`: as wide as their text measured in their font, an even number of points, the text centered from the font's own height, and placed on pixels. Marks that are shapes are drawn as paths, not as glyphs in a text layer (the plus in the slot, the play mark before the first screen's name, the arrow in the flow point), because a glyph's box is not where the glyph is. A new overlay goes through these; do not hand a fractional point to a layer.
- **Handles**: only the four corners are drawn (`drawnHandles`); a side is taken hold of anywhere along it (`resizeHandle(at:)`), which leaves the middle of the right side for the point flows start from (`flowHandleCenter`, a filled disc with an arrow, `nodeRadius`). A view too small on screen for handles has none (zoom in, or use the Inspector), and its flow point stands just outside it.
- **Arrows are built to meet things exactly** (`Arrow`): the line starts on the view's edge and stops at the back of the head (`headLength`), so its round end never shows past the tip, and the tip is on the screen's edge. A side arrow's label sits on the line in the middle of the room between the two screens (`Board.gap` is 200 so there is room for it zoomed out); one that goes round underneath has it at its lowest stretch. A way back goes wherever the person came from, so it is dashed and says Back (`FlowArrow`): to each screen beside it that has a flow to its screen, an arrow; when that screen is further away (an arrow would go round underneath and tangle with the forward one), a short mark out of the screen labelled "Back to <screen>"; with nothing known to lead there, the same mark labelled Back.
- **Getting around**: scrolling pans and a pinch or Command-scroll zooms, as before; the space bar held makes a drag move the board; Command-0 shows every screen, Command-1 the true size, Command-= and Command-- step. A double-click on a screen's title renames it in place (`beginNameEditing`).
- **The right-click menu** fits what is under it: on a view, Step Into, Edit Text, "On Tap, Go To" (every other screen, and Back), order, Duplicate, Delete; on an arrow its styles with the current one checked and Delete Flow; on a screen Rename, Make First Screen, Duplicate, Add Screen, Delete Screen; elsewhere Add Screen.
- **Arrows** are drawn for `store.flows`: from the view to its screen's frame, round underneath when a screen is between, with the style in a pill that picks the arrow too; ways back are dashed (see above). An arrow that starts at the selected view or ends at the selected screen is drawn in the accent color. A selected view has the flow point on its right edge: dragged to another screen it offers the styles, to its own screen Go Back, to empty room a new screen to go to. An arrow is selected as its patch (`store.show`), so the Inspector shows Style and Response and Delete removes it.
- **Agents**: `add_view` kind `screen`, `add_flow {from, to, style?}` or `{from, back: true}`; `get_document` marks screens (`"screen": true`) and lists `flows`. A view an agent adds with no `parent` goes on the selected screen or the first (`AssistantToolbox.defaultParent`, also for `insert_component`); `parent: "device"` (or `"screen"`) is the root, over every screen. `view_prototype` and `interact_prototype` take `screen` to start their run there (`ViewerSnapshot.bitmaps(startScreen:)`), and the Viewer's replay of it starts there too (`replayInViewer(_:from:)`). `AgentServerTests.anAgentBuildsScreensAndFlowsOverMCP` does all of it over MCP. `AssistantPrompt.flowExample` is run by a test as written. The sketch guide maps `NavigationStack`, sheets and navigators to screens and flows.
- **`CanvasInteractionTests`** sends presses, drags and keys to a real `CanvasView` in a window that is never shown (`windowPoint(forBoard:)` says where a board point is) and reads the document back: selecting through levels, moving and snapping, moving between screens, reordering in a stack, resizing, drawing into the open view, retyping a text, the flow handle (`flowChoices` is what its menu offers; the menu itself is not opened in tests) and deleting an arrow. A change to the Canvas's mouse handling gets a test there.
- **Where the Viewer starts is marked**: the play mark before a screen's title on the Canvas (in the accent color when it is not the first), and "Start" after its name in the outline (`store.startScreen`). On that screen, Preview from Here becomes Preview from the Start.
- The examples are `Gallery` items `flow` (Screens and Flows: Push, Modal, back, and swiping back) and `morph` (Card to Screen: a card that grows into its own screen with Morph). `RandomizedTests` adds, moves and unmakes screens and draws flows.
- Limits: every screen has the device's size; frames cannot be placed freely on the board; swipe back is from the left edge of a pushed screen only (no edge gestures of a person's own); the Canvas does not play the prototype.

## The device player

Spec 7.9 (a companion player; device mirroring). An iOS app that runs prototypes with the same engine and renderer, under real fingers: the gallery's examples, and the prototype in the Mac's front window, live, as it is edited. What the Mac sent is kept and plays later with no Mac.

- **The phone runs the real thing**, not a stream of pictures: `PrototypeHost` (PaperHost) with a `Runtime` and a `LayerRenderer`, in `PlayerView`, the player's one UIKit view. It forwards every `UITouch` as `touchBegan(id:)`… (the lowest number no finger has, so one finger is finger 0), runs a `CADisplayLink` at up to 120 Hz that rests when `needsAnotherFrame` is false, and plays video while it is in a window.
- **The screen is fitted** to the phone with `Viewport.fit`, filling it; a phone of another shape shows black beside it. `PrototypeHost.step` fits it again when an edit changes the device's size, since the view's own bounds do not change then.
- **Only what is on screen makes sound**: `PlayerView` sets `PrototypeHost.isOnScreen` as it enters and leaves a window, which stops video and on-device speech (`AppleIntelligence.quiet`), so the live prototype the store keeps after Close is never heard over another.
- **One thing plays at a time**, in one full-screen cover (`Playing`): an example, a kept prototype, or what the Mac sends. Another prototype from the Mac comes up over whatever is playing; an edit to the one already sent does not, so once closed it stays closed and its row under Your Mac brings it back. The phone does not sleep while something plays.
- **Every touch is the prototype's.** The status bar is hidden and the system's edge gestures are deferred, so a prototype's own swipe back works. Three fingers held down bring up the player's bar (Restart, Close).
- **What does not run on the phone yet**: extensions (`PrototypeHost.registry(for:)` registers what a document carries as unavailable, so its patches keep their ports and run nothing), AI patches other than Apple's on-device ones (a cloud model fails at once with `PrototypeHost.noAI`; Transcribe does not record there), and device services (haptics, camera, microphone, location, sound; effects reach `onEffect`, which nothing hears yet). There is no keyboard for text fields.
- **`project.yml`** has the target `TangoPlayer`. `Player/Signing.xcconfig` is committed and includes `Player/Signing.local.xcconfig` if there is one: put `DEVELOPMENT_TEAM` and a `PRODUCT_BUNDLE_IDENTIFIER` you own there to run on a phone. The simulator needs neither.
- **`-example <gallery id>`** on the command line opens an example at once, and `-tap x,y` taps it a second later (`simctl` sends no touches); `scripts/player-shots.sh` uses it to take the player's pictures in the simulator beside `papertool viewer`'s. It compares nothing: look at them.
- **`PrototypeHostTests`** (in `PaperEditorTests`) holds how the host fits the screen, finds points on it, keeps state over an edit and runs none of the extensions a document carries. No test compares what it draws with what the Mac's Viewer draws, and nothing tests pixels on iOS: `scripts/player-shots.sh` puts the two side by side to look at.
- **What iOS does differently**, found in the simulator: a view's layer is y-down there, so `LayerRenderer.flipsRoot` is off (`ShaderSurface.flipsRoot`, for the root a `CARenderer` draws, stays on); SF Symbols are drawn through `UIImage`; and text inside a shader view showed twice when the pixel density changed after its first drawing, so `LayerRenderer` draws a text layer again at once when it does.
- Not checked: touch in the simulator (`simctl` sends none), a real phone, and the glass shader's frame time on one.

### Play on iPhone: the live link

```
EditorView  ->  DeviceLinkBridge  ->  DeviceLink  ->  LinkServer  == TLS with the key ==  LinkConnection  ->  PlayerStore  ->  PrototypeHost
```

- **The Mac sends the whole prototype every time it changes**, and the phone runs it. `DeviceLinkBridge` (beside `ViewerWindowBridge` in `EditorView`) hands `DeviceLink.shared` what the Viewer gets, from the front window only: `store.runtimeDocument` in `store.package`, `restartToken`, `previewScreen`. While the link is off or no phone is connected its trigger is a constant, so an edit costs nothing.
- **`LinkMessage.update`** carries everything about the prototype but its files: an id (a hash of the file's path, or one per untitled window), a revision, `restartToken` and `startScreen` (in every update, because updates are skipped and a restart sent alone could be lost with one), `keeps` (off while a component is edited, when the document is a preview), and the assets and carried extensions by SHA-256. The payload is the document, compact JSON, zlib (`LinkCoding`). The phone asks for the files it lacks (`need`, `blob`), so a video crosses once.
- **Latest wins, one in flight** (`LinkOutbox`, a pure value): the Mac sends a phone its next update only when the phone has said `applied` or `refused` for the last, and what waits meanwhile is only the newest. `DeviceLink.build` encodes, compresses and hashes off the main actor, one at a time, and only while a phone is connected; `LinkHashes` remembers a file by its bytes' storage, as `VideoFiles` does. Whole documents, not diffs: `Runtime.update(document:)` keeps state, and skipping documents is safe.
- **The phone** (`PlayerStore`): `LinkInbox` holds an update until every file it names is here and is what its hash says, then the same prototype id updates the running `PrototypeHost` (state kept, a finger down included) and another id makes a new one. A document from a newer app is `refused` with a reason the Mac shows beside the phone.
- **Pairing is a key in a QR code** (`LinkKey`, 32 random bytes, `tango-link:…`). It keys TLS as a pre-shared key (`LinkTransport.parameters`: TLS 1.2, `TLS_PSK_WITH_AES_128_GCM_SHA256`, the classic `NWListener`/`NWConnection` API, which is the one that takes a PSK). Not a typed code: a short one can be guessed from a recorded handshake. **Session resumption and tickets are off**: with them a connection with the wrong key was let in on an earlier one's session, which `aPhoneWithTheKeyTalksAndOneWithoutDoesNot` caught; keep that test. Each side keeps the key in its keychain (`KeychainLinkKeyStore`); New Code makes another and drops every phone.
- **Finding**: the Mac advertises `_tango._tcp` with peer-to-peer on; the phone browses (`LinkBrowser`, started again when it fails and when the app comes back to the front) and connects to a Mac it found. A Mac that is not the paired one fails the handshake, so after a connection that ended before a hello the next try is the next Mac in the list, after a wait that doubles up to fifteen seconds (`PlayerStore.wait(after:)`). Both Info.plists name the service and say why (`NSLocalNetworkUsageDescription`).
- **Off by default** (`deviceLinkEnabled`): the toolbar's iPhone button (`DeviceLinkButton`) and Settings have the switch, the code and the phones connected (`DeviceLinkPanel`). Only `DeviceLink.shared` advertises and uses the keychain; tests and `papertool link` make their own with `advertises: false`, which listens on loopback only.
- **What comes off the wire is not trusted**, though only a paired device gets this far: a key can leak, and a Mac can be someone else's. Asset names and extension paths end up on the phone's disk, so an update whose names could leave their folder is refused (`Update.hasSafeNames`; `FileWrapper` writes a child named `../x` outside the package). The document is inflated with a limit (`LinkCoding.inflate`), not whole and then measured. A file is kept only if it was asked for and is what its hash says, each is sent once however often it is asked for, a prototype names at most `Update.mostFiles` files and holds at most `LinkInbox.mostBytes`: the Mac does not send one that is more (`LinkSnapshot.make` throws), and a phone sent more anyway lets the update go and says `refused`, so the Mac is not left waiting for an answer. `LinkFrame.parse` copies nothing until a frame is whole, so a video arriving in pieces is not copied each time. The Mac holds at most `DeviceLink.mostPeers` connections and drops one that has not said hello in `helloWait`. A file too large for a frame is a `problem` the panel shows, not a phone left waiting. `PaperLinkTests` has a test for each.
- **A prototype that is closed stays closed**: `DeviceLink.close` empties every outbox before it says `close`, and the phone lets go of an update still waiting for files (`LinkInbox.close`).
- **The window that was in front last is the one sent** (`OpenDocuments.shared.front`), also while another app is in front, so an agent building from a terminal shows on the phone.
- **A pairing key the keychain will not hand over is not replaced** (`LinkKeyStore.isUnreadable`): making a new one would unpair every phone. The panel says so.
- **`hello`** carries the protocol version (sides that differ do not talk) and `PrototypeHost.kinds`, a hash of the patch and view kinds a build knows: when they differ each side says the other is a different version.
- **Tests**: `PaperLinkTests` (frames cut at every byte, forged and unasked files, the outbox, the key, and the one socket test of the transport), `DeviceLinkTests` (the editor's `DeviceLink` to a `PlayerStore` to its `Runtime` over loopback TLS: an edit with a finger down, a restart, a drag of sixty documents, another key, a closed prototype, a connection that never says hello; they set `helloWait` long, since other tests hold the main thread for seconds), and one that reads the QR code back as a camera would. `papertool link card --edit "Hi"` with the player started `-linkkey <key> -linkhost 127.0.0.1:47900` shows it in the simulator.
- **The library** (`PlayerLibrary`): every update that was shown and is to be kept (`keeps`) is written as a `.tango` package in Application Support/Prototypes, with a small PNG of its first frame and an index (`library.json`), under the prototype's id, so the same document replaces its copy. It is written once nothing has arrived for `PlayerLibrary.pause` (each update starts the wait again, so a drag on the Mac writes nothing until it ends), and at once when the app leaves the foreground (`flush`). Writing is on the main thread, with the picture: a prototype with a large video stops the phone for a moment when it is kept. An id comes from outside, so only its letters, digits and hyphens name a file. A `.tango` opened from Files or AirDrop (`onOpenURL`, the document type in the player's Info.plist) is copied in under an id made from its document, so the same file opened again is the same entry. A package made with a newer tango is refused with a reason. `PlayerLibraryTests` holds this with a `later` the test runs itself.
- TLS with a pre-shared key has no forward secrecy: someone who records the link and later gets the key can read what was sent. New Code ends what a lost key can do from then on.
- Not checked, since they need a person: a real finger on the glass, finding the Mac over Bonjour, macOS's and iOS's local-network questions, and scanning the code with a camera. Not built: `status` is defined and never sent; whether AirDrop hands a `.tango` package over whole has not been tried; only the front window's prototype is sent, to every paired phone alike.

## Shader views

Spec 7.8. A view drawn through Metal code the person (usually an agent) writes.

- **A shader view is a View with a setting**, like a stack: `Layer.shader` (`ShaderUse`: the source and the stored values of its inputs) makes `Layer.type` `.shader`. So it holds views, can also be a stack or grid, is stepped into, and Change To keeps its children and cables.
- **The source** is Metal Shading Language: `float4 shader(Frame frame, Inputs in)` and an optional `struct Inputs`. `ShaderSource.interface(of:)` (PaperEngine, text only) reads the members of `Inputs` as inputs (`float`/`int` number, `float2` point, `float3`/`float4` color, `bool`), takes the value after `=` as each one's default, and blanks comments and those defaults in place so the compiler's line numbers are the person's. `ShaderCompiler` (PaperRender) wraps it in a prelude (`Frame`, `content`) and an entry point, and reports the first error as "Line N: …". `ShaderUse.template` is what a new one starts with and what the agent reference shows.
- **Inputs are ports on the view's patch**, with ids prefixed `shader.` (`ShaderUse.portID`) so an input called `opacity` is not the view's own. `normalize` mirrors the source onto the view patch's `script`, which is how `PatchRegistry.ports(for:)` knows the ports without the layer. Values live on the layer (`ShaderUse.inputs`); `store.setLiteral`/`literal` route there, and `store.setShader` drops values and cables that no longer fit. `settlePublished` removes a cable left on an input that is gone.
- **The code is an input too**: `ShaderUse.codePort` ("Code", text) comes first among the shader's ports. Its row says "Edit…" and a click opens the code pane; `literal`/`setLiteral` read and write the source. A text cable into it replaces the source in `ResolvedShader` for that frame (empty text leaves the view's own).
- **Code that arrives by cable adds its inputs to the patch.** It is only known while the prototype runs, so `store.noteArrivingShaderCode` (called from `frameDidTick`) writes it to `ShaderUse.arriving` when it is not the view's own; this is not an undo step. The patch's inputs are `ShaderSource.uniforms(of:)`: the own code's, then those only the arriving code declares, so switching between looks loses no cable. `normalize` mirrors it to `PatchNode.arrivingScript`; `Document.forgetUncabledShaderCode` drops it once nothing is cabled into Code. Only the last arriving code is remembered.
- **At run time** the cabled inputs of a view patch that start with `shader.` go to `ResolvedLayer.shader` (`ResolvedShader`: source, values, time) through `setShaderInputs`. A shader whose source mentions `time` keeps `needsAnotherFrame` true; any other costs nothing while idle.
- **Drawing** (`LayerRenderer.sync`, `ShaderSurface.draw`): the view's fill and children go into a layer that is not on screen, which `CARenderer` draws into a Metal texture; the shader reads that as `content` and writes an IOSurface, which is the `contents` of a layer inside the view's own. Corner radius, border, shadow, opacity and transforms stay Core Animation's. Shader views are drawn after the frame's transaction is committed, innermost first. An IOSurface shows up in `CALayer.render(in:)`, so snapshots, recordings and thumbnails need nothing special.
- While the source does not compile the view keeps drawing with the last source that did (or shows what is in it, unchanged). With no Metal device it is an ordinary view.
- **Editing:** the code opens in a pane under the patch graph (`ShaderEditorPane`, `store.editingShader`; Patch > Edit Shader…, Shift-Command-E, the patch's context menu, or the Inspector's Shader section). The text is a `CodeTextView` (an `NSTextView`) colored by `ShaderHighlighter`, a regular expression over the text, which also marks the line a compile error names. It applies what is typed after a short pause as one undo step per burst, and follows changes made elsewhere (undo, the assistant).
- **Agents:** `add_view` kind `shader` takes `shader` and `inputs`; `set_shader {view, shader?, inputs?}`; `connect` takes an input by its name. `get_document` gives the source, `in`, `inputs` and `shader_error`. Code that does not compile fails the operation and is rolled back. `AssistantPrompt.shaderExample` is run by a test, like the other two, and every shader in `AssistantPrompt.shaderRecipes` (shown whole in the reference) is compiled by one. After each operation of a batch `store.settleArrivingShaderCode` runs the prototype for three frames without a Viewer, so an agent can cable code and then cable to that code's inputs in the same batch.
- **A shader can read what is behind its view**: `behind(frame, point)`, in the view's own coordinates and up to `LayerRenderer.behindMargin` (32) points outside it. `ShaderSource.Interface.readsBehind` says whether the source calls it. Such a view is drawn after the others, back to front: `LayerRenderer.picture(behind:)` takes the picture the way Background Blur does (the root's `render(in:)` with the view and everything painted after it hidden), `ShaderCompiler.texture(from:)` hands it to Metal, and it is taken again on every frame that is drawn. `BackgroundBlurTests` checks it pixel for pixel with a shader that only returns `behind`.
- Limits: what a shader reads behind its view is what is on the screen, so one inside another shader view sees nothing there; views inside are clipped to its bounds; a live Camera view or a blinking caret inside one only moves when something else asks for frames.

## Icons, fonts and photos

Not in the product spec. Icon sets, typefaces and stock photos from outside the app, as patches and as values a view stores. What is shipped and what is fetched follows each one's licence and terms:

| | Ships in the app | Fetched | Kept in the document |
|---|---|---|---|
| SF Symbols | the system's | — | — |
| Lucide (ISC) | every icon (`Catalogs/lucide.json`) | — | — |
| Material Symbols (Apache 2.0) | the names (`material-symbols.json`) | each glyph as SVG from `fonts.gstatic.com`, once | yes, `web.<set>.<name>.<variant>.svg` |
| Google Fonts (OFL, Apache, UFL) | the families (`google-fonts.json`) | each style's TTF through `fonts.googleapis.com/css2`, once | yes, `web.font.<Family>.<style>.ttf` |
| Apple's families | the system's | — | never (Apple's licence; every device has them) |
| Unsplash photos | — | every run, with the person's key | never (Unsplash asks for hotlinking and credit) |

- **Icons are a Symbol view's name.** `symbol` is an SF Symbol as before, or a set and a name: `lucide:heart`, `material:home`, `material-rounded:favorite.fill`, `material-sharp:…` (`IconName`). No new view type or property, so cables, the Inspector and old documents are untouched. Lucide and Material are drawn here from vector shapes (`VectorGlyph`, `SVGPath`, which reads all of SVG's path grammar), fitted into the view's frame; `fontWeight` is Lucide's line width (`weight / 200`) and Material's weight (100–700, only the 24-point optical size). The renderer draws Lucide itself and asks `iconProvider` for Material.
- **Type has a family.** `fontFamily` (empty for SF Pro) and `italic` are properties of a text and a text field. `FontBook` (PaperEngine, Core Text only) turns family, weight and slant into one `CTFont` for both `TextMeasurer` and `LayerRenderer`, so text takes the room it is drawn in. SF Pro Rounded, New York and SF Mono are the system font's designs (the `NSCTFontUIFontDesignTrait` trait AppKit itself uses). `FontBook.systemFamilies` is only Apple families on both macOS and iOS; add one only after checking it on both. A family that is not here yet is set in the system font until its file is registered (`FontBook.register`, process-wide, idempotent, through a file in the temporary folder). A document's font is registered only when its asset names a Google family and the font is that family, so no document can replace Georgia or SF Pro for every open document; keep that check.
- **Fetching is the host's** (`WebAssets.shared`, PaperHost): memory, then a cache in Caches/Tango/Web, then Google (`fetchFromGoogle` refuses any other host; `transport` is replaced in tests). Arrivals post `WebAssets.didArrive`; the Viewer, the Canvas and the player then ask for a frame (`Runtime.setNeedsFrame`) and lay out again. `WebAssetClient.attach(to:)` gives a renderer the `iconProvider` and `onFont` hooks; `fetches` is the host's `sendsRequests` (the Canvas's is the store's `keepsWebAssets`), so pictures, `papertool editor --canvas` and the assistant's hidden runs fetch nothing and draw only what the document carries. Each render also collects the `web.` assets it drew and reports the whole set when it changes (`onDrawnWebAssets`).
- **The document keeps what it uses** (`DocumentWebAssets.swift`): with `keepsWebAssets` on (the app's documents, from `PaperDocument`), the store looks after each burst of changes at what its stored values name (Symbol views, texts, the Icon and Font patches' literal inputs) and what each Viewer or Canvas renderer drew in its last render (`setDrawnWebAssets`, which replaces that renderer's last report, for names a cable chose), copies the arrived files into `assets`, and drops a `web.` asset only once it was seen in use this session and no longer is (`usedWebAssets`): a file a document comes with stays until then, since a cable may pick it once the prototype runs. An Icon or Font patch is kept at the weights of the views it feeds. Not an undo step. Assets travel to the phone like any other, so the player draws them offline; `FontBook.register(assets:)` runs whenever assets change (store, `PrototypeHost`).
- **Patches** (category Media, `MediaPatches.swift`): **Icon** (`icon`: Set, Name, Filled → Symbol, Known), **Font** (`font`: Family → Font, Source), **Unsplash Photo** (`unsplashPhoto`: Search, Orientation, Index, Next, Size → Image, Photographer, Profile, Description, Color, Count, Loading, Error). Unsplash Photo sees its whole loop (`.wholeLoop`, whose `LoopContext` now has `requests` and `replies` too), so a loop of indexes is one search and one row per index; a photo that failed is not asked for again until another search or a restart; its API requests carry `NetworkRequest.service` `unsplash`, which only built-in patches can set, and the Viewer adds `Authorization: Client-ID` only for `https://api.unsplash.com` (`Unsplash.signed`). Pictures come from `images.unsplash.com` only, kept by the host as `fetched:<request id>` (`ScriptReply.id`). Each photo shown is reported once to its `download_location`, as Unsplash's guidelines ask. The key is `AIKeys` account `unsplash`, in Settings > AI. The player refuses Unsplash requests (the key stays on the Mac).
- **In the Inspector**: Font and Italic rows under Text, with a searchable list of every family (`FontPicker`); the Symbol row has an icon browser (`IconPicker`, Lucide drawn, Material by name). Both are in `AssetFields.swift`.
- **Agents** read "Icons, fonts and photos" in the reference (`AssistantPrompt.assets()`, generated from the catalogs; `assetsExample` is run by a test), and outside agents a mapping from lucide-react, vector-icons, Jetpack icons, `.font(.custom…)` and expo-google-fonts in the sketch guide.
- **Catalogs**: `python3 -I scripts/update-catalogs.py` rewrites them from npm (lucide-static) and Google's metadata. Lucide's licence ships beside them.
- **Tests**: `MediaAssetTests` (engine: paths, every Lucide icon in its box, names, fonts with the ABeeZee fixture in `Tests/Fixtures/fonts`, Unsplash's requests and key) and `WebAssetTests` (editor: a document keeps and lets go of what it uses, with a fake Google).
- Limits: Material at one optical size and grade; no italic for SF Symbols or icons; a Google font on the Mac but not yet in a document draws in the system font in `papertool viewer`; Unsplash's rate limit (50 an hour for a new app) is the person's to watch; the phone cannot search Unsplash; a Material or Google file that only a script's text names is fetched again on a Mac without it until the Viewer has drawn it once.

## Video views

Spec 7.7 (media layers: video). A view that plays a movie.

- **A stored kind** (`LayerKind.video`, `ViewType.video`), like Camera: it holds no views. Its properties are `video` (an asset's file name or an http(s) address), `contentMode` (Fill, Fit), `playing`, `loops`, `time`, `playbackRate`, `muted` and `volume`, plus the usual ones; `fill` is what shows around a picture that does not fill it (black).
- **The runtime owns the playhead** (`Runtime.advanceVideos`, after layout): per repetition (`ResolvedLayer.Hit`), a change to `time` jumps there, a playing video advances by `dt × playbackRate`, and at an end it wraps (`loops`) or stops there; played again after stopping, it starts from the other end. It writes `ResolvedLayer.playhead` (time, isPlaying). Only a moving video (or one that just reached an end) keeps `needsAnotherFrame` true; a paused one, a rate of 0 or an empty `video` costs nothing. `restart()` clears playheads.
- **The host says how long a video is**: `runtime.setVideoDuration(_:for:)`, by the `video` value; until then a video plays on with no end. `LayerRenderer.onVideoDuration` reports it, and `ViewerView` passes it on. Durations survive `restart()`. A video the host cannot load (a missing asset, an address that is not a movie, a player that failed) is reported with `setVideoUnplayable` and stands still, so a typo costs no frames; a duration arriving later or `restart()` clears it. Times go to AVFoundation through `videoTime`, which clamps, since `CMTimeValue(Double)` traps.
- **Video Time** (`PatchKind.videoTime`) is how the playhead gets out, since view patches have no outputs: attached to a video like View Size, it reports time, duration, progress, playing and an ended pulse as of the end of the frame before (`videoRows`). `DocumentStore.viewKind(for:)` says it fits only a video (Text Input only a text field); the outline's Touch menu, the Patch Library and `add_patch` go by it.
- **Drawing follows the playhead** (`LayerRenderer.showVideo`). With `playsVideo` off (the default: pictures, `papertool viewer`/`record`, the assistant's hidden runs, the gallery, the Canvas) each frame is the picture at exactly the playhead, made at once by `VideoStills` (AVAssetImageGenerator, cached), so it is the same every time; a web address shows a placeholder and nothing is fetched. `ViewerView` turns `playsVideo` on only while its window is visible (`syncVideo`, by occlusion), and then a `VideoPlayer` (AVPlayer and AVPlayerItemVideoOutput) plays it with sound at the prototype's rate, seeking when it drifts more than a quarter second or the playhead jumps; its frames go on the layer as IOSurfaces, so a recording made from the Viewer has them. A file at rest shows its still. The Canvas shows the frame its stored `time` names.
- **Files**: an asset is bytes in memory and players read files, so `VideoFiles.url(for:assets:)` writes each one once to a temporary folder under a name from a hash of its bytes. The Inspector's Video row takes a typed address or Choose…, which copies a movie into the assets as `ImageField` does for pictures.
- **The example**: `Gallery` item `video` (Video Scrubbing) plays `Media/Sunset.mov`, a four-second clip that `papertool sample-video` draws in code with frequent keyframes. `GalleryItem.assets` carries it into `item.package()`, which the gallery, `papertool` and `Examples/` use.
- Limits: no subtitles, picture-in-picture or sound in recordings; a video from the web plays only in the Viewer, and its length is unknown (so it never ends) in pictures; played backwards where AVPlayer cannot, the Viewer follows by seeking frame by frame; agents can name a web address but cannot add a file to the assets.

## The iOS shelf

Spec 7.3 ("familiar iOS … interface elements"). The system's controls, bars, rows and presentations, ready to drop in, so nobody rebuilds a switch to try an idea. UIKit cannot draw inside a macOS app, and every pixel of a prototype has to be the same in a picture as in the Viewer, so these are replicas made of views and patches. A view drawn by Apple's own code was tried as a spike and is not built: a bare Mac Catalyst process with no window does build real UIKit controls and draw them in about 10 ms, in the iPad idiom, but `CALayer.render(in:)` leaves out what iOS 26 draws with glass (knobs come out square, a stepper, a navigation bar and a search field's body are missing), and `drawHierarchy` throws without an app and a window. So the real thing needs a helper app with a real window whose pixels come back from the window server: late, and not the same in a picture as in the Viewer. That is a device player's job more than a painter's.

- **Two sorts of thing.** A component (`ComponentDefinition`, in `ComponentLibrary.iOS`) is a control with inputs and outputs. A template (`ViewTemplate`, in `ComponentLibrary.templates`) is a container that holds a person's own views, which a component cannot: a tree of plain views, the patches that run it (kept inside its root: `template(…)` sets their `home`), and the ports its root publishes. `store.insertTemplate` copies it in under new ids through `Clipboard.insert`, as a paste does. `ComponentLibrary.groups` (Controls, Bars, Lists, Presentations) is the order both are listed in.
- **What is on it.** Controls: Button (Style: Filled, Tinted, Gray, Plain), Toggle, Slider (Minimum, Maximum), Stepper (Value, Minimum, Maximum, Step), Segmented Control, Text Field, Search Field, Menu Button, Progress Bar, Activity Indicator, Page Control. Bars: Status Bar, Navigation Bar (glass buttons for Back and an Action, no bar behind them), Large Title Bar (Scroll Offset), Tab Bar (a floating capsule of glass as wide as its tabs; Floating off makes it a flat bar), Toolbar (round glass buttons), Home Indicator. Lists: List Row (Subtitle, Symbol, Accessory: Chevron, None, Checkmark, Switch; Separator), Swipe Actions Row; templates List Section (Header and Footer, each with a Shows switch, the footer hidden to begin with) and Form. Presentations: Alert, Action Sheet (a card in the middle; a tap outside cancels), Context Menu, Keyboard (a picture: typing still comes from the Mac); template Sheet.
- **Files**: `Library/ComponentLibrary.swift` (the list, `make`, `stabilized`, the layer helpers, the Builder's `input`/`output`/`bound`/`place`/`wire`), `SystemStyle.swift` (tokens and `Look`), `Controls.swift`, `Bars.swift`, `Lists.swift`, `Presentations.swift`, `Templates.swift`, and `SystemKitSample.swift` (the `kit` gallery item: a Settings screen from the shelf alone, three cables).
- **Tokens.** `SystemStyle` has the system colors in both appearances (`Dynamic`), the text styles and the measures. A new control takes its numbers from there.
- **The measures were taken from a phone**: a screenshot of Settings on an iPhone 17 Pro with iOS 26 (402 × 874 points), read pixel by pixel beside a picture of the `kit` example at the same scale until the two agreed to about a point. A status bar is 62 points; a row's content stood 20 in, its symbol a 28-point tile 17 in with the text at 58, a chevron ending 22 from the edge and a switch 18 (the rows are now SwiftUI's, from the simulator: see below); a switch is 63 × 28 with a 37 × 24 knob; the line between rows is a point thick from the text to 20 short of the edge; a grouped section has 26-point corners, 16-point margins, and 35 points to the next (46 with one line of footer). That phone's text was one size down from the default (body 15, rows of 50): the text styles here are the default ones and a row is 52, which is inferred from the line height and not measured. Colors were not matched: the two pictures' color spaces differ.
- **A section's captions are the text views' own words**, published as they are, so the Canvas shows what the Viewer does; whether each shows is its row's `visible`, published too. The footer's row is 4 points high with its words reaching past it: that is what makes the space after a section right both with a footer and without, with nothing to compute.
- **Dark is an input, not the Mac's appearance.** What a person draws around a control has fixed colors, so a control that followed the Mac would turn dark alone on a light screen, and only in the Viewer. Every component has a `Dark` input (`Look`, which adds it and one `if` per color); the List Section and the Sheet publish one. Cable Device Info's Dark Mode in to follow the device.
- **Ids never change.** A document stores a component's id and the ids of the ports it cables (the Component Input and Output patches). `stabilized` names a view's patch after its view and every other patch after its place among those, so a control can be given another view at any time; a patch is only ever added after the ones a shipped control has. `shippedViews` is the view count of each of the first eight controls, whose ids were made when views counted. `Tests/Fixtures/library/ids.json` holds every id that has shipped and `LibraryIDTests` fails if one moves; record new ones with `TANGO_LIBRARY_IDS_OUT=1 swift test --filter LibraryIDTests`. A document keeps the copy of a component it adopted: a control that got better is new for documents that have not used it yet.
- **Placement** (`ComponentDefinition.Placement`, optional, and on a template): `top` and `bottom` give a new use the screen's width at that edge, against the bars already there (`store.barEdge`: a navigation bar lands under the status bar); `fill` covers the screen (Alert, Action Sheet, Sheet); `bottomOverlay` lies along the bottom over whatever is there and takes no room from the bars (the Home Indicator, which a Tab Bar's 21 points of clear room are for). A place that was asked for is kept.
- **A chosen segment or tab is one pill that slides** (`Sliding`), measured against iOS 26's motion. A Segmented Control's segments and a Tab Bar's tabs keep their own fill and Pill, clear now, because the loop into a segment's fill is what repeats it and the patches keep their ids.
- **Presentations** share `Presenting`: a `Presented` input, a `Present` pulse, a Switch that remembers and a spring from 0 to 1, with the root's `visible` off while nothing of it shows, so what is behind it is touched again. Each dismisses itself and says so (`Dismissed`, `Chosen`, `Showing`).
- **Patches the shelf needed**, which anyone can use: Counter has Step, Minimum, Maximum and Start (limits count when Minimum is below Maximum); Switch has Starts On; Loop Option Switch has a Picked output (also for the copy already picked); Either joins two pulses; Gate lets a pulse through while a condition is on.
- **A template's port must not be named like a view's own input** (the Sheet's is "Sheet Height"): both are on one patch and found by name. `LibraryTemplateTests` holds that.
- **In the interface**: the Patch Library lists the shelf (`LibraryItem.component`, `.template`, category `.shelf`), in its groups, with a picture of each (`LibraryPreview`, made once from a hidden run); the toolbar's Components menu and the Component menu have the same groups. Extension shelves are listed there too.
- **Agents**: `insert_component` as before; `insert_template {template, name?, parent?, properties?, ref?}`; `set_inputs` on a view that publishes inputs sets those by name. The reference lists every component and template with its ports, and the sketch guide maps SwiftUI and React Native controls to them.
- **Text of several lines is measured as tall as all its lines**, leading included (`TextMeasurer.measure`): the size Core Text suggests leaves the last line's leading off, and a `CATextLayer` given only that drops the last line and runs its words off the edge of the one before. One line is measured as before. `TextMeasurerTests` draws it as the renderer does.
- **Text is measured at the weight it is drawn with** (`TextMeasurer.weightTrait`, the renderer's nine steps); before, medium and semibold were measured as regular and bold.
- **`LibraryQATests`** is where a way the shelf went wrong is written down: every component with odd inputs (empty and endless text, numbers at a billion, every choice and one that is not a choice) and odd sizes under a wandering finger, which must stay finite, come to rest and never take seconds to play (a Page Control asked for a billion pages did; it now shows thirty at most); saving and reading; undo; copies of a template; the selected screen; and the names agents find ports by. `TANGO_LIBRARY_QA_FULL=1` runs every odd input, about a minute; one in eight run otherwise.
- **Looking at the shelf**: `TANGO_LIBRARY_PICTURES_OUT=<folder> swift test --filter everyShelfItemHasAPicture` writes a picture of every item; `swift run papertool viewer kit out.png` shows them together.
- **Bars are glass, not slabs**, as on iOS 26: the buttons of a Navigation Bar and a Toolbar are glass over the content, and only the Large Title Bar has a material (`SystemStyle.bar` with Background Blur), which comes in as its title collapses.
- **Liquid Glass is a shader** (`SystemStyle.glassShader`, `Library/Glass.swift`), fitted to iOS 26's own glass (see the glass cases below). Over `behind`, in linear light: a wide blur (Blur, 24 points) with a share of what is behind still sharp (Detail, 0.3), seen through a lens at the rim that shows what is further in (Refraction 25 over a Rim of 19), under a light veil (Tint, white at 0.275), then made more vivid on the stored values (Vibrancy, 2) so color comes through the veil; light catches the edge (Shine) and the views inside are drawn on top. Radius must be the view's corner radius. `ComponentLibrary.glass(…)` makes such a view, and the shelf's glass (the Tab Bar, the Navigation Bar's and Toolbar's buttons) uses the shader's own numbers: `SystemStyle.glassRefraction`, `glassShine` and `glassTint` are written into it, so they cannot drift apart. The Tab Bar floats unless Floating is turned off (flat against the edge, no lens and no light), and the Glass template under Materials is a pane of it to put anything on. It is also the first of the shader recipes agents are shown. 128 samples a pixel: it costs more than a plain view while it is drawn, nothing at rest.
- Limits: the glass is a look, not Apple's (no light that moves with the device, no merging of two panes that touch, no lifting under a finger); alerts and menus are opaque, and a sheet's glass is a translucent fill with Background Blur, not the shader; the keyboard's keys do nothing, and a tap on it takes focus from the field as any tap elsewhere does; a Menu Button's menu and a Context Menu are drawn in their place in the tree, so a later sibling can cover them; a component already in a document is not updated when the shelf's is; no Button sizes, date or wheel pickers, or search bar with Cancel.

## Holding the shelf against real SwiftUI

A rig that says, in points and in red, how each component differs from the real thing. Not in the product spec.

```bash
Reference/run.sh                 # every case: build the reference app, take its pictures, compare
Reference/run.sh tab-bar alert   # only these
REFERENCE_KEEP=1 Reference/run.sh tab-bar   # compare again with the pictures already taken (after changing ours)
REFERENCE_DARK=1 Reference/run.sh            # the same in dark appearance: shots-dark, redline-dark
REFERENCE_MOTION=1 Reference/run.sh          # the moving cases: recordings in motion, the report in motion-redline
```

- **The real side** is `Reference/ReferenceApp.swift`: one SwiftUI screen per case, compiled straight with `swiftc` for the iOS Simulator (no Xcode project), installed on an iPhone 17 Pro simulator (402 × 874, as the shelf is drawn for) in light appearance at the default text size, and opened case by case with `simctl launch … -case <id>`; `simctl io screenshot` takes each picture. A control alone stands with its corner at (20, 100) on the gray of Settings. The simulator composites real iOS, so this is true Liquid Glass.
- **Our side** is `ReferenceCase.all` (`Library/ReferenceCases.swift`): for each id, a document that should look the same and the part of the screen to compare. A new case needs an entry in both, under one id; no test checks that the two lists agree.
- **The comparison** is `Redline` (PaperEditor; pure functions on pixels, with no tests of their own: the rig is run by hand): the box round each one's content, how far ours is off in x, y, width and height, where each has edges along the lines through its middle, the share of pixels that differ, and a picture of the real thing, ours, and the real thing washed out with what differs in red. `papertool redline <pictures> <out>` writes them and `report.md`; `<out>/ours/` has our whole pictures, to measure with anything else.
- **Reading it**: a size off by a point or more is a real difference. The share of pixels that differ is small for a control alone on a whole strip of screen, so read it against the same case before a change, not against other cases. Colors differ a little everywhere (the simulator's blue is the newer system blue).
- **What it has settled**: every case is within a point or two, most within half a point, with about 1% of pixels differing or less (the list, 1.6%, is mostly the Dynamic Island). The Toggle, Text Field, Progress Bar, Activity Indicator, Alert and Action Sheet are exact. Rebuilt from it: the Tab Bar (a capsule as wide as its tabs, 86 points each, 62 high, 21 above the bottom, nearly clear glass with a hairline and a faint shadow); the Slider (a 6-point track and the switch's pill for a knob); the Text Field (white with a hairline, 34 high); the Alert (a gray card 320 wide with two gray capsules, neither tinted); the Action Sheet (a card of glass 240 wide in the middle of the screen with no Cancel, as a confirmation dialog is on iOS 26); the Navigation Bar and Toolbar (no bar at all: glass buttons, their words and symbols the color of text); the Large Title Bar draws nothing until its title has gone into the row; the Search Field (44 high, as `.searchable` draws it under a large title, the glyph the color of text; that case compares it there, not alone); the Activity Indicator (20 points, UIKit's medium); the Sheet (iOS 26 floats a sheet that is not full height: 8 points in from the sides and the bottom, glass over the dim, top corners 36, a 56 × 4 grabber); the Keyboard (iOS 26's: a panel with corners of 26, a strip of suggestions, white keys 43 high, capitals, the emoji and dictation buttons under the last row); and the status bar's places. A list row is 52 points with its content 16 in, as a SwiftUI `List` has it (Settings stands it 20 in). `SystemStyle.glassTint` is only a shade lighter than what is behind, as the real glass is.
- **Where the two still differ and why**: the Dynamic Island, soft shadows, the simulator's newer blue, the Sheet's bottom corners (53 on the phone, following its own; a view has one radius, so ours are 36) and the hairlines round glass (outside its edge there, inside ours), and a few symbols drawn a point larger or smaller than Apple draws them at the same size (the tab bar's person, the keyboard's Delete and Return). The Activity Indicator's picture is taken mid-turn, so which spoke is darkest differs. The list case draws Settings' tiles in SwiftUI (`Tile`), since a bare `Label` has none.
- **The glass cases** (`glass-checker`, `glass-stripes`, `glass-circle`) put a pane of `.glassEffect(.regular)` over a checkerboard of black and white and over stripes of pure red, green, blue and yellow (pure, so neither side's color space changes them), and ours, with the shader's own inputs, over the same backdrop drawn by a shader view. `papertool glassfit <shots> name=start:step …` searches the shader's inputs (and `tintLevel`, `tintAlpha`) for the least mean difference over the panes, `Redline.glassError`; a run takes a minute or two. What it found: the real glass mixes light in linear terms (a checkerboard comes out 195 and 224, which is 72% wide blur and 28% sharp under a 29% veil, in linear light), keeps color vivid under the veil, and its lens bends what is further in. The mean difference went from 17.9 (of 255) to 5.6, and pixels that differ from 26%, 45% and 18% to under 1%, 3.4% and under 1%. What is left: the real glass's thin dark rim and its own soft shadow, and the stripes' colors at their purest.
- **Dark appearance**: `REFERENCE_DARK=1` takes the simulator's pictures in dark, and ours are `ReferenceCase.makeDark()`: each case with every component's Dark input on, a template's Dark value on, the grouped background dark and glass given its dark tint (`papertool redline … --dark`, `glassfit … --dark`). Every case holds in both, within 1.6% of pixels, but the stripes under glass in dark (10.8%: dark glass keeps color deeper than one Vibrancy for both appearances gives). What dark found: the glass's dark tint (gray 0.174 at 0.655, the gray real dark glass lifts black to), the selected tab's pill near black, a stepper's body near black (`SystemStyle.stepperFill`, not the gray of a track), and the keyboard's board and keys (32 and 68 gray, every key alike).
- **The Dynamic Island** is in some of the simulator's pictures and not others, and the shelf draws none: `Redline.dynamicIsland` is left out of every comparison.
- **A picture of the simulator has a few black pixels in its very corner**; `Redline.content` leaves them out, or every region that starts at the top of the screen measures to the corner.
- **Motion** (`ReferenceMotion`, `Library/ReferenceMotions.swift`; `RedlineMotion.swift`): a toggle turning on, a segmented control and a tab bar choosing, a sheet, an alert and an action sheet coming up, a push and a full-screen cover (our Modal). The reference app's `MotionCase` makes each change from code 5 seconds after it opens (the simulator takes no taps from a script), while `simctl io recordVideo` records the screen; ours is the same document at rest, tapped where `tap` says (a presentation has a screen-sized Trigger view whose Tap sets it going), with a picture every sixtieth of a second. A recording holds a frame only when the screen changed, so `Redline.clip(ofVideo:)` holds each frame until the next, starts at the frame held longest (the case at rest, not the launch) and ends at the last change: the recording must outlast the motion. Each side is measured against itself: progress is each frame's change from the first projected on the whole change to the last (so a color that differs everywhere does not count), and time 0 is where it passed 5%; a `Track` is a line along which the first edge is found in every frame (a knob, a sheet's top, a pushed screen's edge). The report gives half way, 90%, settled (within 2%), overshoot and how far apart the curves are, with a filmstrip, a chart per measure and a CSV. Progress cannot show a slide overshooting (a box past its end is only unlike its last frame); the tracks do. `REFERENCE_DARK` works with it.
- **What motion found, and what was changed for it** (light): the sheet (1.1%) and the alert (1.7%) already moved as the real ones do. The segmented control faded its chosen segment and the tab bar switched its pill at once; on iOS 26 one pill slides and stretches toward the new choice, so both now have one (`Sliding`, `Library/Sliding.swift`: each edge follows a quick and a slow spring and takes the one further out, so the edge in front leads either way; it reads the copies' frame outputs; until the first choice its springs follow at once, so nothing slides in as the control appears; it says how much of each copy the pill covers, which turns a tab's tint and a segment's bold as the pill comes over them), from 10.1% and 17.8% to 4.6% and 4.1%. The toggle's track fills more slowly than its knob slides (its own spring, 0.45): 12.4% to 5.3%. Push and Modal settled in 400 ms where the real ones take 260 to 300: `Navigation.defaultResponse` is 0.33 (was 0.45): 8.3% to 3.8% and 3.9% to 1.1%. The real push starts faster than our critically damped spring. The real action sheet appeared within a frame in two recordings; ours fades in over half a second and was left so, until a recording made another way says otherwise.
- Not compared yet: the Context Menu and the Swipe Actions Row (they need a long press and a swipe, which `simctl` cannot send), and the Home Indicator. The keyboard case needs the simulator's hardware keyboard disconnected (I/O > Keyboard), as it is by default.
- Limits: still pictures only; a picture of the simulator has no home indicator; the status bar's glyphs are Apple's own and not SF Symbols; each capture waits 4.5 seconds for the launch screen to go, so a full run takes over a minute.

## Background blur

Spec 8 ("glass and material effects, background effects"). Any plain view can blur what is behind it.

- **A property**, `backgroundBlur` (points, 0 by default), of a view, a stack, a grid and a scroll view; in the Inspector under Appearance, and an input on the view's patch like any other. With a fill that is partly clear the view is a material.
- **Drawing** (`LayerRenderer.backdrop`, `drawBackdrop`): such a view has a layer under its children holding the blurred picture and, over it, the view's fill (the view's own layer has no background then). After the frame's layers are in place and shader views are drawn, each blurring view, back to front, takes a picture of the tree with itself and everything painted after it hidden (`CALayer.render(in:)` of the root, only where the view stands, at half size), blurs it with Core Image and shows it. The picture is taken the way snapshots are, so it is the same in the Viewer, on the Canvas, in a recording and with no window.
- It is made again on every frame that is rendered and costs nothing while the prototype is idle (about 2 ms a frame for the two blurred bars and the glass tab bar of the `kit` example). The radius, and how far a shader reaches behind its view, are in the prototype's points: both are scaled by the zoom the view is shown at (`LayerRenderer.zoom(of:)`), and a view that is not in the tree on screen (one inside a shader view) is given no picture. `BackgroundBlurTests` checks pixels: the right way up, in place off-center and partly off screen, the fill over the blur, and nothing in front of the view in its picture. A view tested must not stand the same distance from the top as from the bottom: the first version read the mirrored place, and every such test passed.
- Limits: the picture is of what is on the screen, so a view inside a shader view blurs nothing; a view in something turned or scaled blurs the box around itself; the blur of a container that is itself partly clear counts that container's opacity twice.

## How the editor works

- **The patch graph is the main workspace.** The window is the outline of views (sidebar), the graph, and the Inspector. The canvas is an optional pane above the graph (`store.showsCanvas`, Option-Command-C, off by default, remembered in the defaults): every screen side by side, edited in place, with the flows between them (see Screens and flows). The toolbar's Fit fits the graph and the board (`store.requestFitCanvas`).
- **The app opens with a welcome window** (`WelcomeView`, a `Window` with `.defaultLaunchBehavior(.presented)`, which keeps `DocumentGroup` from showing its Open panel at launch): New Prototype, Start from an Example (the gallery) and Open… on the left; on the right the recent documents with a picture of each first screen (`WelcomeRecent.list`: Tango files still there, not the gallery's temporary copies), or a few examples (`WelcomeView.featuredExamples`) while there are none. It closes itself once a document window comes forward; Window > Welcome to Tango (Shift-Command-1) brings it back.
- **Settings is three toolbar panes** (`AgentSettingsView`, a `TabView` in the `Settings` scene, as a Mac app's settings are): General (what recordings and the Viewer show), AI (providers and keys) and Agents (the MCP server, the commands to connect, the sketch requests). A pane is one grouped `Form`, as tall as what is in it; AI is the long one and scrolls. Wording follows the Mac's: section titles and buttons in title case, switches and row labels as sentences, a footer under a section for what it means, a status beside a provider's name with a checkmark as well as a color. A new setting goes in the pane it belongs to, not in a new window.
- **The window toolbar** is laid out like Origami's: the Views | Assistant switch and the sidebar's one button over the sidebar; Insert (a click opens the Patch Library, its arrow lists views, components and a comment) beside the title; Canvas and Fit, then Device, Viewer and Restart in the middle; the Inspector on the right. Icons only, no labels.
- **One selection.** `store.selectedNodes` is it; `selectedLayers` is computed from it (the views whose patch is selected), and setting it selects those patches and scrolls a single one into view. Do not add a second stored set.
- **The Inspector follows the selection.** One view: its properties (`inspectorSections`). One patch that is not a view (`store.selectedPatch`): `PatchInspector`, with its name (`renamePatch`), type for a generic patch, input count, its inputs as the same `ValueEditor` controls (`setLiteral`, so each edit is an undo step), a cabled input naming where it comes from (`store.cableSource`) with what arrived, and its outputs with live values (`store.liveValues`, `Value.liveSummary` for loops) and where each goes (`store.cableTargets`), both followed through the ports that publish it, where a cable from outside wins; the names are links that `store.show` the other patch.
- **The Patch Library** (`PatchLibraryView`, Option-Space, Patch > Library…, Return in the graph) is a popover: search, a sidebar of categories, the list, and a pane explaining the selected item. What that pane says beyond the summary is `PatchGuide` (PaperEngine): details, a tip, a note per port and search tags for every built-in patch and view type. A new patch needs an entry there, or `PatchLibraryTests` fails; search ranks the name, then the tags, then the text (`LibraryItem.search`).
- Views are added from the Patch Library (its first section), the toolbar's Add View menu or the Insert menu (`store.addView`): the new view goes inside the selected container. Deleting a view's patch deletes the view; renaming it renames the view; editing a value on it is `store.setInput`, the same as the Inspector.
- `DocumentStore` owns the document. Every change goes through `apply(name) { }` (one undo step) or `interactive { }` … `endInteractive(name)` (a drag). `transaction(name) { }` wraps several `apply` calls into one undo step.
- **Device templates** (`DeviceTemplate` in `PaperModel`: iPhone 18 Pro 402 × 874, Desktop 1400 × 900) size the screen. The Device picker in the toolbar (`DevicePicker`) calls `store.setDevice`; new documents start at iPhone 18 Pro (`Document.blank()`), while a stored document without a size keeps the old 390 × 844 default; only the size is stored, so a size matching no template shows as Custom. The Viewer follows the screen's proportions. Add a device by adding it to `DeviceTemplate.all`; the assistant's prompt lists them.
- The leading sidebar shows either the outline of views or the Assistant, switched by a segmented control in the sidebar's part of the toolbar as Xcode switches navigators (`store.sidebarMode`, `store.showsSidebar`, bound to the split view's column visibility). The trailing column is the Inspector only (`store.showsInspector`). The sidebar's toolbar keeps one button after the switch in either mode (Group, or New Chat) so the switch does not move.
- **Editing inside a component:** `store.document` is then a view of the component as if it were a document (root layer as the screen, its graph as the graph), so editing code needs no special cases. Use `store.fullDocument` only for what must see the whole file (saving, component lists).
- The Canvas shows stored layer values (the document's graph is not run) but does run component internals, so instances show their configured state. Every screen is there at once, each in its own frame.
- **The patch graph sits on a 12-point grid** (`PatchGrid` in `PaperModel`, which also holds the patch metrics so `normalize` can find room for a new view's patch). Every `PatchLayout` measure is a whole number of units, so a patch on the grid has its ports on the grid and aligned ports give straight cables. Anything that places a patch snaps it (`PatchGrid.snap`); dragging snaps unless Command is held. Keep new layout constants multiples of 12.
- **Cables go around patches.** `PatchEditorView.Cable` is one curve unless that would run behind a patch that is neither of its ends: then it drops (or rises) in the gap before the patch, runs along its edge and goes on to the input, and a cable that runs backwards turns round and passes over or under everything between its ends. It takes the shorter way that is clear, and stays one plain curve when neither is. `CableRoutingTests.noCableInTheGalleryRunsBehindAPatch` holds every example to it, so place an example's patches in rows and columns that leave it room.
- **Cables show live data.** `PatchEditorView.frameDidTick` notes when each connected output last changed; for a moment after, the cable carries moving beads and a capsule naming its value. A selected patch keeps the labels on everything upstream of it. The view redraws only while something is moving, and beads are skipped under Reduce Motion.
- The Viewer is an independent floating `NSPanel`, deliberately not a child window: child windows stutter when dragged. Over it the pointer is a round touch cursor (`ViewerView.touchCursor`), because prototypes are for phones. It is a system cursor, so a recording cannot capture it.
- **Recordings show touches by default.** For each recorded picture `ViewerView.recordedTouches` says which fingers are down (or just lifted and fading for `touchLinger` seconds, so a quick tap is visible), and they are drawn as layers for that one picture only; a resting pointer and an Option finger that is not pressing are left out. The switch is Prototype > Show Touches in Recordings and Settings (`recordsTouches` in the defaults); `startRecording(touches:)` and `papertool record --no-touches` override it. A tap that does not come from the mouse should go through `ViewerView.tap(at:)` so it shows too.

## How the assistant works

The chat in the leading sidebar (Views | Assistant) builds layers and patches on request. It is not in the product spec.

```
AssistantView  <->  AssistantSession  <-- JSON lines on stdin/stdout -->  Assistant/sidecar.mjs (Claude Agent SDK)
                         |
                    AssistantToolbox  -->  DocumentStore
```

- **Who answers is a provider** (`AssistantProvider`: Claude, OpenAI, Gemini, Local), and a model is a provider and an id (`AssistantSession.Model`, a struct; the lists per provider are in `AssistantProvider.swift`, OpenAI's being the Generate Text patch's). `AssistantProvider.transport(for:)` picks the line: `ProcessTransport` (the Node program and the Agent SDK) for Claude, `ChatTransport` for everyone else. A session or `AssistantChats` given a `makeTransport` uses that instead, which is what tests do.
- **`ChatTransport` is the loop for everyone who is not Claude**, in Swift, with no Node, streaming and with tools, in one of two dialects (`ChatTransport.Dialect`, from `AssistantProvider.dialect`): `completions` (OpenAI's Chat Completions, which Gemini at `generativelanguage.googleapis.com/v1beta/openai` and local servers such as oMLX, Ollama and LM Studio speak) and `responses` (OpenAI itself: its newer models refuse function tools on Chat Completions; sent with `store: false` and `include: reasoning.encrypted_content`, every output item sent back as it came, tools not `strict`). Everything that differs between the two is in `ChatRequest` and `ChatStream`; the loop is one. It sends the chat the same messages the sidecar does, so `AssistantSession` does not know which it has: `ChatStream` reads the stream, `ItemScanner` (the sidecar's, in Swift) finds each operation of a call while it is written, so these models build live too. `ChatRequest` builds what is sent as plain functions (the four tools come from `AgentServer.tools`, without `document` and without a list of choices on a number, which Gemini refuses); `lines` is replaceable, and `ChatTransportTests` plays a server through it. A tool's pictures follow its answer as a user message, since a tool message carries none; a model that is not shown pictures is told there was one. A call's extra fields are sent back as they came (Gemini's thought signature). A call whose arguments are not JSON is answered as an error and what streamed from it is taken back (`tool_abandoned`). Thinking levels above high go as high; a local server gets none. Words that follow a tool round start apart from the ones before, as the sidecar's do. Requests go through `PrototypeNetwork.session` and `guarded`, so a local address typed in Settings cannot drive the app's own agent port. Eighty requests an answer at most, as the sidecar.
- **Keys are the AI patches' keys** (`AIKeys`, now by account name: `anthropic`, `openAI`, `gemini`, `local`; the `AIProvider` calls forward). Settings' AI pane (`AISettingsPane`) has a section per provider, each with its status beside its name, its key (`APIKeyRow`) and a footer saying what it answers in: Claude, with whether the assistant signs in with this Mac's Claude account (the default) or the saved key (`assistantClaudeUsesKey`; `ProcessTransport(apiKey:needsKey:)` adds `apiKey` to `start`, and the sidecar uses a key only when sent one, never one from the environment); OpenAI; Gemini; and Local Models (`LocalModelsSection`): which server (a preset or Other), its address, an optional key, Connect, which lists the server's models into the defaults for the menu (a changed address forgets them), and whether pictures are sent (off by default). The composer's menu has a section per provider; one with no key, or no local models, offers Settings. The last model chosen starts the next document's chat (`assistantModel`).
- Limits: OpenAI by key only (no ChatGPT sign-in, which only the Codex agent offers); Gemini through its OpenAI-compatible endpoint, not `generateContent`; no request has been made to a real OpenAI, Gemini or local server from here, so the Responses events and Gemini's signatures are as their docs and others' bug reports describe them; the Gemini ids and oMLX's port were read from their docs in November 2026 and not tried against a live account here; a small local model may not manage the reference or the tools, and nothing is trimmed for it.
- The model has no file or shell tools. Its only tools are `get_document`, `edit_document`, `view_prototype` and `interact_prototype`, defined in `sidecar.mjs` and answered by the app through `AssistantToolbox`, which calls the same `DocumentStore` commands the interface uses.
- Pictures are offline: `ViewerSnapshot` makes its Viewer with `sendsRequests: false`, so a Network Request patch stays loading and nothing leaves the Mac (the gallery's thumbnails included). A `.look` after a touch first runs the two frames the prototype needs to see it.
- `ViewerSnapshot.bitmaps(of:steps:)` runs taps, drags, held fingers (`down`, `move`, `up`, each for finger 1 unless `finger: 2` names a second one beside it), typing, pinches (two real fingers 88 points apart that spread, turn and travel by `pan`), hovers and waits on a fresh prototype and draws it at each `.look`; `view_prototype` and `interact_prototype` both use it.
- `edit_document` takes a batch of operations and runs it in `store.transaction`, so one batch is one undo step. A failed operation is reported back, anything it had already changed is put back, and the rest still run. A view or patch is looked up by ref (this batch's, then one an earlier batch gave while what it named is still there: `store.agentRefs`, not saved), then exact name, then id (the full 8-character short id, so a view called "A" is never mistaken for the start of an id). A script that does not compile, or runs too long, is an error. New patches are laid out left to right afterwards, level by level, below what each level already had. Afterwards only what is in the open level is selected, so Delete never reaches a level that is out of sight.
- The operations speak of views: `add_view` (kinds are `ViewType` names), `set_properties` with `x`/`y`/`width`/`height`, `change_view`, `set_ports`. A view can be named wherever a patch is expected, so `connect` has one form, `{from, output, to, input}`; an agent never sees a view patch's own id (`describe` writes cables with the view's id).
- `publish_port`, `unpublish_port` and `rename_port` work on published ports; once published, a port is reached by its name on the containing view in `connect`, like a component's.
- Agents are told to build with containers and published ports: the reference has the sections "Views inside views" and "Reading get_document". `get_document` gives `open_view` (the level the person is in) and the operation `open_view` shows them one. The example batches in the reference are `AssistantPrompt.tapExample`, `publishExample` and `shaderExample`, and a test runs them as written; keep it that way when changing an operation.
- **References** (`AssistantReference`: a view, a patch, or `AssistantMedia`) are what the person points the assistant at. They wait in `store.assistantReferences` and the composer shows them as chips; `session.send` takes them and empties the list. They get there by `store.addToAssistant` (Command-L, "Add to Assistant" in the graph's and the outline's context menus, a click on the dashed selection chip), by typing "@" and part of a name (`AssistantMention`), and for pictures and videos by the paperclip, a drop on the panel or Command-V (`session.attach`). What is selected still travels with every message without being held.
- `AssistantMessage.make` writes what the model reads: a note in square brackets naming the selection and each reference (id, kind, cables by name), then the pictures, each after a label. A video is not sent as video: `AssistantMediaLoader` takes 4 to 12 stills spread over its length (`frameTimes`), 768 pixels at most, labelled with their times. Pictures are JPEG, 1568 pixels at most. The sidecar's `user` message carries them as `images`.
- **The prototype is built while the model writes.** A big `edit_document` batch takes a minute to write, and the call only arrives whole. The sidecar follows each call's JSON as it streams (`ItemScanner`) and sends `thinking`, `tool_start` and one `tool_item` per operation or step the moment it is complete, each with the call's `useId`; `AssistantProgress` words them for the status line, naming what a ref or id points at (`AssistantToolbox.name(for:in:)`) ("12 changes planned · Adding text “Temperature”…"). For `edit_document` the session also applies each operation as it arrives (`AssistantToolbox.beginEdit`, `apply(_:to:)`, `finishEdit`, the same steps `edit` takes at once), inside one store transaction held open across the event loop (`store.beginTransaction`/`endTransaction`), so the whole batch is still one undo step. When the call arrives it is matched by `useId`: operations the stream missed are applied then, and a call that differs from what streamed is rebuilt from the call. A call the SDK refused on the way (`tool_abandoned`) is taken back; Stop, `done` or a dead process keep what was built, laid out. New patches are laid out once, at the end. Edits the person makes while a batch is being written fold into the assistant's undo step. `session.buildsLive` turns it off; `AssistantLiveEditTests` holds it.
- **An answer says where its time went** (`AssistantTiming`, on the answer's last entry as `Entry.timing`, only for answers of `AssistantTiming.worthSaying` seconds or more): waiting for Claude, thinking, writing, writing changes, using the prototype. The session moves it between phases as events arrive, reading `session.now`, which tests replace.
- **Several chats per document**, as in Cursor or Claude Code (`AssistantChats`, held by `EditorView`): each is an `AssistantSession` with its own line to Claude, draft and queue, and the ones not shown go on answering. New Chat (the sidebar toolbar's one button, View > New Chat, Option-Command-N) starts one beside the others unless the one shown has not begun. Once a chat has begun, a header above the transcript has a glass menu naming the chat shown, whose icon moves while any chat is answering and fills when another has an answer not yet seen (`finishedAnswers`, `hasUnseenAnswer`); its menu lists every chat with the same icons and deletes. Beside it, a glass Delete Chat button. View also has Show Next/Previous Chat (Option-Command-] and [) and Delete Chat; the menu bar has no list of chats, since commands are not drawn again when chats come and go. Choosing another model in a chat that has begun starts a new chat with it (`setModel`) rather than wiping it. Deleting a chat stops its line; the document keeps every change.
- **Chats build the document at the same time**, so: every batch a chat applies holds the store's shared transaction (`holdTransaction`/`releaseTransaction`: the first hold opens it, the last release closes it), so overlapping batches are one undo step whichever finishes first; a chat never goes back to where its batch began (an abandoned call, a call unlike what streamed) when another chat built meanwhile (`holdsBegun`); and each chat keeps its own refs (`withOwnRefs`), as outside agents keep the store's. `AssistantChatsTests` holds all of it. Chats are not saved with the document.
- A message sent while an answer is in progress waits in `session.queued` and goes out at `done`. Stop holds the queue until the person sends it (`sendNext`) or removes it.
- An answer that changed the document ends with a `.changes` entry holding the document before and after. Its Undo is offered only while the document still equals `after` (Redo while it equals `before`), and steps the undo manager until it gets there.
- **The Viewer shows the assistant using the prototype.** `view_prototype` (with a tap) and `interact_prototype` still get their pictures from a hidden, instant run; the toolbox then hands the same steps to `store.replayInViewer`, and the live `ViewerView.replay` plays them from a restart at a speed a person can follow, with the assistant's fingers as accent-colored layers and an "Assistant" badge. It is a showing of the run, not the run: the live Viewer sends network requests and the hidden one does not. AI patches are the exception: during a replay their Send and Record fail with `ViewerView.notSentDuringReplay`, so an agent checking its work never spends the person's credit, speaks or opens the microphone. `ViewerSnapshot.beats(for:paced:)` is the one place that says what a step means, frame by frame, for both; `paced` never moves the prototype's own time: the finger travels during frames in which nothing else happens (a wait), the prototype stands still for it where there are none (`Frame.ticks` 0), and a wait longer than two seconds is hurried through (`ticks` above 1) rather than cut. During a replay the Viewer ticks the runtime a sixtieth at a time from those frames, not from the display, so a double tap, a delay or a spring caught mid-way is the same for the person as it was for the assistant (`theReplayIsInStepWithTheHiddenRunEvenMidAnimation`). A touch, a key or a Restart from the person cancels the replay; one asked for during another waits, and only the newest waits. A replay does not start while the person is touching the prototype or the Viewer is out of sight, runs the document as it is at that moment, lasts a minute at most (`ViewerSnapshot.longestPacedRun`), and ends by lifting whatever finger or hover the steps left on the prototype (`letGo`). Outside agents get it too, since it is in the toolbox. Prototype > Show Assistant Using the Prototype (`showsAssistantTouches`) turns it off. `papertool record <doc> out.mov --replay '<steps json>'` records one.
- **Everything the chat is drawn with is in `AssistantStyle`**: its colors (plain tints of the primary color, not the system's layered styles, which came out different from box to box), two corner radii, three text sizes, the icon column, and the pieces built from them (`assistantBox`, `AssistantRow`, `AssistantIconButtonStyle`, `AssistantBoxButtonStyle`). A new piece of the chat takes its numbers from there; do not write a radius, a font or an opacity into a view. New Chat sits after the Views | Assistant switch in the sidebar's toolbar (`EditorView`).
- The chat is `AssistantView` (transcript, queue, drop and paste), `AssistantComposer` (chips, "@" suggestions, controls, `FlowLayout`) and `AssistantMarkdown` (headings, lists and code fences; `blocks(of:)` is tested). An action entry carries its symbol and, after a look at the prototype, the picture the model saw.
- `papertool editor <doc> out.png --assistant "<request>"` draws the window with a conversation played by `RehearsedTransport`, for looking at the chat without Claude. `--appearance light|dark` picks the appearance (dark by default), and `--assistant ""` shows the empty chat.
- `AssistantPrompt` generates the system prompt from the code: every view type and its properties, every patch in the registry, every library component. A new patch needs no prompt change. A new `edit_document` operation needs a line in the prompt and a case in `AssistantToolbox.perform`.
- `sidecar.mjs` and `package.json` are SwiftPM resources. On first use `ProcessTransport` copies them to `~/Library/Application Support/Tango/Assistant/` and runs `npm install` there (about 370 MB, it includes a Claude Code binary). Never run `npm install` inside `Sources/`: the whole folder is copied into the app.
- Auth for Claude: by default the SDK uses the Claude login on this Mac (`claude auth login`). That is for personal testing; Anthropic does not allow shipping claude.ai login in a third-party product, so a distributed build should answer on the saved key (the Settings choice above). `papertool assistant` reads other providers' keys from `OPENAI_API_KEY`, `GEMINI_API_KEY` and, for a local server that wants one, `LOCAL_API_KEY`.
- The model menu is `AssistantSession.Model`: full model ids, Claude's shown by name and version ("Opus 5.5"), others as their ids. Update the ids in `AssistantProvider.swift` when a new generation ships. "Default" sends no model and shows the one Claude reports back. The same menu has Thinking (`AssistantSession.Effort`, the Agent SDK's effort levels): it goes out in `start`, and a change mid-conversation is an `effort` message the sidecar applies with `applyFlagSettings`, so it needs no new chat. The app's session starts on the last model chosen, or Opus (`AssistantSettings.model`).
- Tests use `FakeTransport`, never the real process. To try a real turn without the app: `swift run papertool assistant empty "Make a card that grows when tapped"`. A shell started by Claude Code carries its own `CLAUDE_CODE_*` login variables, so run that from a normal terminal.

## How outside agents drive the app

Claude Code, Codex or any MCP client can do what the built-in assistant does, on the documents open in the running app. Not in the product spec.

```
Claude Code / Codex  -- POST http://127.0.0.1:47821/mcp -->  AgentListener  ->  AgentServer  ->  OpenDocuments  ->  AssistantToolbox  ->  DocumentStore
```

```bash
claude mcp add --transport http tango http://127.0.0.1:47821/mcp
codex mcp add tango --url http://127.0.0.1:47821/mcp
```

- **Outside agents build in steps.** Their calls reach the app whole, so the live building the built-in assistant gets cannot happen for them. `AgentServer.pacingGuide` (first in `get_reference`, since Claude Code saves an answer that long to a file and its agent may read only the start; and a clause in `instructions`) asks for one `edit_document` per screen or section of a big build, so the person sees it grow; it overrides the reference's "as few calls as you can" for them only.
- `AgentServer` is the protocol with no sockets: JSON-RPC data in, data out (`initialize`, `ping`, `tools/list`, `tools/call`). Tests drive it directly. `AgentListener` is a small HTTP/1.1 server on `Network.framework`, bound to 127.0.0.1. It answers `POST /mcp` with plain JSON and refuses `GET` (there is no server-to-client stream). No dependency and no Node.
- Tools: `get_reference` (the text of `AssistantPrompt.reference`, since an outside agent has no system prompt from us, then `AgentServer.pacingGuide` and `sketchGuide`), `list_documents`, `get_document`, `edit_document`, `view_prototype`, `interact_prototype`, `undo`, `redo`, and for sketches of code `mark_baseline`, `get_changes`, `compare_prototype`. All but the first two are `AssistantToolbox` calls, so a new toolbox tool needs a schema in `AgentServer.tools` and nothing else. An agent's batch is the undo step "Agent Edit".
- Every document tool takes an optional `document` (id or name from `list_documents`) and otherwise uses the front window. `EditorView` registers its store with `OpenDocuments.shared` while it is on screen; a document that leaves the screen and returns keeps its id.
- `AgentService.shared` starts the listener from `EditorScene.init`, so `papertool` and tests never open a port. It is on by default; Settings (Command-comma), the Agents pane, has the switch, stored as `agentServerEnabled`. If port 47821 is taken it tries the next nine, and Settings shows the commands with the real port.
- Any program on this Mac can reach the port; there is no token. `HTTPRequest.comesFromThisMac` refuses a `Host` that is not a loopback name (which stops DNS rebinding) and any request that carries an `Origin` at all: browsers send one for everything a page can post here and coding agents never do, so this keeps out web pages, including ones served by another program on this Mac. Keep that check if the listener changes.
- What an agent sends is checked in `AssistantToolbox`: numbers must be finite and within `limit` (`number`, `whole`), because a layer with NaN or infinity cannot be drawn or saved and JSON cannot write one. An edit that arrives while the person is mid-drag first closes their change as its own undo step (`store.finishInteractive`).
- The built-in assistant's `sidecar.mjs` offers the same tools except `get_reference`, `list_documents`, `undo` and `redo`. A new tool for it needs an entry in `sidecar.mjs`; pictures go back as `images`.
- To try it by hand: `curl -s http://127.0.0.1:47821/mcp -H 'Content-Type: application/json' -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'`.

## A scratch pad for code

A screen that lives in code (SwiftUI, React Native) can be sketched here, played with, and the changes carried back. The app never reads code: the person's coding agent does both directions over MCP, and the code stays the truth. Not in the product spec.

- **Pull:** the agent reads the code and builds the screen with `edit_document`, writing `source` on every view and patch (`Layer.source`, `PatchNode.source`: free text such as `ProfileScreen.swift:57 statsCard`), checks it with `compare_prototype {path, tap?, seconds?}` (a picture of the real screen beside the prototype, and the share of pixels that differ), then calls `mark_baseline`.
- **The starting point** is `Document.sketch` (`Sketch`: a source and a `Baseline` of screen, graph and components). `store.markBaseline` writes it on the whole document, also while a component is open, as one undo step. Both it and `source` are optional fields, so older files open and the version is still 4.
- **Push:** `get_changes {pictures?}` is `SketchChanges.report()`: the baseline against now, matched by id. Views changed (each property `from`/`to`, x/y/width/height apart), renamed, moved, reordered, added (with `parent` and `after`) and removed; patches and cables by title; components once, inside. `motion` lists every Spring and Easing that is new, changed, or whose range changed, with what it drives (followed through Transition patches), what starts it, and its numbers as SwiftUI and Reanimated write them (`springCode`, `easingCode`; a test steps a real mass and spring against `Spring.step`). The agent edits the code and marks the baseline again.
- `AgentServer.sketchGuide` teaches all of this and is appended to `get_reference` for outside agents only: how the code's structure, tokens (one `value` patch per token), state (a `switch` named after the `@State`) and motion map onto views and patches, with a SwiftUI and a React Native table. Keep it in step with what views can do.
- The three tools are in `AssistantToolbox` (`SketchChanges.swift`), listed in `AgentServer.tools` and not in `sidecar.mjs`.
- For the person: the Inspector shows a view's Source; File > Mark as Starting Point and File > Copy Changes for an Agent (the report as text, for an agent without MCP); Settings shows the two requests to make.
- `Integrations/claude-code` is a Claude Code plugin with `/tango:sketch` and `/tango:apply` (`claude --plugin-dir Integrations/claude-code`). The commands point at `get_reference`; the knowledge is in the app, not in the plugin.
- Three things exist because code needed them: a side of a stack can have its own padding (`paddingTop`/`Bottom`/`Left`/`Right`, each following `paddingVertical` or `paddingHorizontal` until stored: `LayerProperty.follows`, honored by `Layer.value` and `ResolvedLayer.value`); `visible` (a view whose `visible` is off is left out of the resolved tree, so it is not drawn, takes no room and gets no touches: what `if` does in code); and the Button component's Corner Radius and Weight inputs.

## How extensions work

People add their own patches, views and components as extensions: local folders of sandboxed JavaScript, Metal and JSON. Not in the product spec. `Extensions/README.md` is the reference for writing one; `Extensions/` holds three (Sampler, Charts, Ask Claude) that `ExampleExtensionTests` uses as a person would.

```
Name.paperextension/extension.json  ->  PaperExtension  ->  ExtensionSet  ->  PatchRegistry.adding(_:)  ->  Runtime / DocumentStore
ExtensionStore (what is installed)  ->  EditorView  ->  store.setRegistry  ->  Viewer, Patch Editor
script: paper.fetch  ->  EvalContext.requests  ->  Runtime.requestHandler  ->  ViewerView  ->  ExtensionNetwork  ->  KeyVault
```

- **The manifest is the interface.** `ExtensionManifest` (`extension.json`) declares every port, host and key; reading it runs nothing. So the install sheet can say exactly what is added, and a document whose extension is missing still shows its patches with their ports and cables. `PaperExtension.problems()` is what does run scripts (to see that they load); it is called only for extensions that are installed, never for a copy a document carries or one being reviewed.
- **Kinds have a slash.** A patch or view of an extension is `<extension id>/<item id>` (`ExtensionKind`); no built-in kind contains one. A manifest `category` is an existing `PatchCategory` name, so no switch grows.
- **An `ExtensionSet` has available and unavailable members.** Installed and switched on is available. Switched off, broken, or only carried by the document is unavailable: `PatchRegistry.adding` registers its patches with their ports and no script (`PatchDefinition.isAvailable`, `origin`, `script`), `registry.library` leaves them out, and the Patch Editor draws them dashed with "Needs <name>" (`store.missingExtension`).
- **Nothing is pruned against a kind that is not known.** `settlePublished` drops cables and published ports whose port it cannot find, which would empty a document opened without its extension. `PatchRegistry.knows(_:)` guards it. `ExtensionTests.settlingNeverPrunesAgainstAPatchItDoesNotKnow` and `ExtensionStoreTests.aDocumentEditedWithoutItsExtensionLosesNothing` hold this; keep them passing when touching `settlePublished` or `normalize`.
- **The registry is passed, never assumed.** Every `Runtime` and `ViewerSnapshot` takes `store.runtimeRegistry`; a new call site that leaves it out runs without extensions. `DocumentStore` gets its registry in `init` (settling runs there) and `setRegistry` afterwards, which bumps `registryRevision` and tells the Viewer (`onRegistryChange` -> `Runtime.update(registry:)`, which keeps the state of every patch whose own script did not change).
- **A script is a JavaScript patch with declared ports** (`Script.Instance(source:ports:report:)`), plus `paper`. A JavaScript patch in a document has no `paper`: a document is not trusted to reach the network.
- **Requests.** `paper.fetch` only writes a request down. `Instance.step` hands it to the runtime through `EvalContext.requests`; `Runtime` gives it an id, remembers whose it is (`scriptRequests`: patch, loop row, the script's own token) and calls `requestHandler` with a `NetworkRequest` that has `headers` and `origin` (the extension id). `complete` is unchanged. On the next tick the answer goes to that patch's row (`EvalContext.replies`), where `step` resets pulses, settles the promise, calls `evaluate`, then reads outputs: what awaited the answer runs inside that one call. Waiting costs no frames. Requests are forgotten when a loop row goes, on `restart()`, and when a patch does not keep its state over an edit.
- **Each entry into a script has `Script.timeLimit` to itself**, continuations after an `await` included (JavaScriptCore's watchdog covers the microtask drain). A cut-off is told by elapsed time, not by an exception, and retires the instance: it is never entered again.
- **`ExtensionNetwork` is the only code that sends an extension's request, and the only code that handles a key's value.** `prepare` is pure and is where every rule lives: the host must be in the manifest's `network`; https only (http to loopback); a key's placeholder (`Script.secretOpen` … `secretClose`, what `paper.secret` returns) is filled in a header or the query, only for the hosts declared for that key, and is refused in a body, in the path, and for any other host; the request is built from the very URL that was checked; forbidden headers are dropped; a request to loopback carries `Origin: null`, which `AgentListener` refuses, so an extension allowed `localhost` cannot drive the app's own agent port. `send` uses an ephemeral session, follows no redirect and keeps no cookie. `scrub` removes the key, in the forms a service would echo it, from what comes back. `ExtensionNetworkTests` plays a hostile script against each rule; add a case there with any change.
- **A key is never put in a body** because a service can be asked to hand content back in any shape, which no scrub catches. Headers and the query are echoed rarely and verbatim.
- **Keys** (`KeyVault.swift`). `KeychainVault` holds values (generic passwords, service `com.tango.extension-keys`, this Mac only); `ExtensionKeys` holds everything else in `keys.json` beside the installed extensions, so listing keys never opens the keychain. A key belongs to one key of one extension and is bound to the hosts that were declared for it when it was entered: an extension's id is only a name, so a version that declares more hosts does not inherit the key (`settle(for:)` on install, `status` `.outgrown` otherwise). `lookup` is called off the main actor, from whatever sends the request. Only `ExtensionStore.shared` uses the keychain; every other store, and every test, uses `MemoryVault`. `ViewerView.keyLookup` is nil unless the app's Viewer panel sets it, so a snapshot or a test refuses a request that names a key.
- **Views an extension draws** are views with a setting, like shader views: `Layer.custom` (`CustomViewUse`: kind and stored input values) makes `Layer.type` `.custom`. `normalize` mirrors the kind to `PatchNode.custom`, so `PatchRegistry.ports(for:)` adds the inputs (ids prefixed `ext.`, `CustomViewUse.portID`) without the layer. Values are on the layer (`store.setCustomInput`; `setLiteral`/`literal` route there). As with a shader's inputs, a loop into one does not by itself repeat the view.
- **Drawing.** The runtime collects cabled `ext.` inputs (`ResolvedLayer.setCustomInputs`); after `laidOut()` a `ViewPainter` runs `draw(canvas, inputs, size, time)` for each such view whose inputs, size or script changed (or that set `everyFrame`) and stores a `Drawing` on `ResolvedLayer.drawing`: `[DrawCommand]`, plain values, compared by a stamp. One JavaScript context per view kind, a cache per resolved view. `LayerRenderer` shows it in a layer under the view's children, made by `DrawingRasterizer` only when the stamp, size or scale changes. `CanvasView` keeps a painter of its own so a drag does not load scripts again. A script is stopped when it runs too long, and so is what it asked to have drawn: `DrawingRasterizer.timeLimit` cuts a picture short, a drawing holds at most `Drawing.limit` steps and `Drawing.mostText` characters, and a view's size is checked as a number before it becomes a pixel count (`aDrawingMeantToTakeForeverIsCutShort`, `aViewOfAnySizeIsDrawnOrLeftOutButNeverStopsTheApp`). The canvas is the HTML canvas's drawing subset (`DrawScript.canvasPrelude`); adding a call means a line there, a `DrawCommand` case, a case in `DrawCommand.read` and one in the rasterizer.
- **A packaged shader is copied in.** `store.addExtensionView` makes an ordinary shader view with the extension's source for a view that names `shader`, as `insertComponent` copies a library component: it works without the extension, and updating the extension does not change it.
- **Components** an extension ships are `ComponentDefinition` JSON (`PaperExtension.components()`), a `ComponentShelf` in `registry.shelves` beside the iOS controls (`store.componentShelves`). `insertComponent` adopts the library components one is made of and copies its pictures from the extension into the document's assets. `ExtensionStore.export` writes one from a document.
- **Documents carry copies, and never run them.** `DocumentPackage.extensions` holds the files of each extension the document uses, under `extensions/<id>/`; `DocumentStore` keeps the best copy it knows (`copies`: the installed one, unless the document came with a newer) and writes those for `usedExtensionIDs`. There is no list in `document.json`: what a document needs is the kinds in it. On open, `ExtensionStore.offers` says what stands between the document and each extension (install the carried copy, update, switch on, enter keys, missing) and `ExtensionOfferBar` shows it above the graph.
- **`ExtensionStore`** (`@Observable`, `.shared` for the app) is what is installed: `~/Library/Application Support/Tango/Extensions/<id>.paperextension`, `state.json` (on or off, where it came from, a linked folder) and `keys.json`. Both files go through `SettingsFile`: one that is there but cannot be read is moved aside as `state.unreadable-<date>.json` (listed under Could Not Be Read, where Remove deletes it) rather than saved over with an empty list, and if it cannot be moved nothing is saved over it; a failed read or save is `store.problem`, shown in the Extensions window until a save succeeds. Updates are found by looking where an extension was installed from (`checkForUpdates`), everything being a local file. A linked folder (Link Folder for Development…) is used where it is, and `refreshLinked`, once a second in the app, reads it again when a file changed. What cannot be read is listed as `broken` and cleared with `remove(_:)`: for a link that removes the link and never the folder.
- **The Extensions window** (`ExtensionManagerView`, Option-Command-E) and the sheet that asks before installing (`ExtensionReviewSheet`) show the same sections (`ExtensionContents`), so what was agreed to reads the same afterwards. An update lists what changes (`PaperExtension.changes(from:)`) and marks what widens.
- **Agents** are told of extensions by `AssistantPrompt.extensions`; `add_patch` and `add_view` take an extension's kind, `set_inputs` with the view as `patch` sets a drawn view's inputs, and `get_document` marks what cannot run with `needs_extension`.
- `ExtensionQATests` is where a way an extension went wrong, or a thing a hostile one might try, is written down as a test: scripts that misuse their ports, drawings meant to take forever, addresses and manifests written to confuse, kinds in a document that are not what they seem. Add to it with any fix.
- Limits: an extension is not signed, so its id proves nothing (hence keys bound to hosts, and copies from documents offered rather than trusted); JavaScriptCore bounds time but not memory; a drawn view has inputs only, and gets its touches from Interaction patches or a component around it; opening a `.paperextension` from the Finder is not handled (install from the window, by drop, or with papertool).

## Conventions

- **UI uses standard Apple components**: SwiftUI, `NavigationSplitView`, `List`, `Form`, `.inspector`, toolbar items, sheets, Liquid Glass. Only the canvas, patch graph and viewer surfaces are custom-drawn AppKit. Do not hand-roll headers, sidebars, selection highlights or inspectors.
- In files that import SwiftUI or Foundation, write `PaperModel.Document` and `PaperEngine.Port`; the bare names are ambiguous.
- New `PortType`, `LayerKind`, `ViewType`, `LayerProperty` or `PatchCategory` cases break exhaustive switches in the model (`Layer.swift`), the editor (`PatchStyle`, `LayerListView`, `PatchLibraryView`, `PatchEditorView.parse`) and in `LayerRenderer`. Build to find them. A new property also needs a place in `LayerProperty.properties(for:)` (both of them) and in `inspectorSections` (`InspectorView.swift`), alone or in a group row that shares a label (Position is X and Y); a property with a few fixed choices can show them as icons in `optionSymbols`.
- A copied view takes along the patches kept in it (`home`), not only the ones attached to it (`DocumentStore.fragment(ofLayers:)`): they are what a container publishes from, and a copy without them has lost its ports and what it does.
- Anything that copies patches under new ids (paste, duplicate, making a component) must also remap `PublishedPort.inner.node`, as `Clipboard.insert` does, and keep each port's `id` (cables and ports published further out name it); a port left pointing at a patch outside its view is dropped by `settlePublished`.
- A patch, view type or renderer change that an extension could also provide should go through the same registry and resolved tree; do not add a second path for extensions.
- New optional model fields must decode from older files: use optionals or `decodeIfPresent`. `Document.currentVersion` is 4 (3 made views patches, 4 gave the graph levels).
- Library component ids must be stable across launches (`ComponentLibrary.stableID`), because documents store them. A patch's id comes from its place among the component's patches that are not view patches, so add new patches to a library component after everything it already has (see the Button, and "The iOS shelf").
- **`RandomizedTests`** builds documents by chance (seeded, so a failure names its seed): random edits through the store's commands and random agent batches through `AssistantToolbox`, with numbers at the edges of a Double. After every edit it checks that settling again changes nothing, that there is one view patch per view and no cable to nowhere, that every stored number is finite, that saving and reading gives the same document, and that undo and redo land on each side of the edit; every few edits it runs the prototype with random touches, checks that every output and resolved frame is finite, and draws it. It runs 40 seeds by default; after touching the model, the runtime or the store, run more (`TANGO_RANDOM_SEEDS=2000 swift test --filter RandomizedTests`; `TANGO_RANDOM_FIRST_SEED` and `TANGO_RANDOM_TRACE` reproduce one, see the file). Pin what it finds with a test of its own (`HardeningTests`).
- Every feature gets tests that drive `Runtime` or `DocumentStore` directly. Tests that register undo need an `UndoManager` with `groupsByEvent = false` and explicit grouping (see `StoreTests`).
- Examples share one look, `ExampleStyle` (`ExampleStyle.swift`): the iPhone 18 Pro screen (a `Builder` gives a screen with no size 402 × 874), room for the status bar (`top`) and home indicator, one palette and set of text sizes, a `hint` pill saying what to try (it listens for nothing, so it takes no touch), and pictures drawn with views (`scene`). Each says in its graph what its patches do with `b.note(_:around:)`, a comment drawn round those patches once they are placed (view patches are left out, since they are moved apart); keep its title short enough for its width, and keep notes from overlapping. The Settings kit (`kit`) keeps the shelf's own measures.
- The gallery's Showcase section (`MarqueeSamples.swift`: `player`, `weather`, `holo`; `OnDeviceChat.swift`: `chat`) is where shaders, glass and motion work together as in a finished app; each shader there takes its look from a few inputs that one spring or script drives. `ShowcaseTests` holds what their hints promise.
- **`Examples/AUTHORING.md`** is the brief for an agent adding a gallery example: what to read, a skeleton that is checked to build and pass, the house rules for comments and layout, and the checks to run. Keep its skeleton working when the Builder or `ExampleStyle` changes.
- Examples are built with `SampleDocuments.Builder`. `b.view(layer, at:)` gives a view's patch a place and returns it; `b.property(.scale, of:at:)` returns a handle to connect to as port "value". View patches nobody placed are lined up to the right when the document is read.
- Every shipped prototype is a `GalleryItem` in `Gallery.items` (`Patterns.swift`): that one list feeds the gallery window (File > New from Gallery, Shift-Command-N), `papertool`, `Examples/` and several tests. To add one, write a builder function and add an item; `PatternTests` then checks its cables and `PatchGridTests` its grid. After changing any, run `swift run papertool examples Examples`.

## Gotchas

- Never write `Int(someDouble)` on a value that comes from a document, a patch or an agent: it stops the app on a number that is too large or not a number (a Loop with a count of -1e308 did). Use `Double.whole`, which clamps. Arithmetic that can overflow into infinity (layout adding huge sizes) ends in `Double.clampedFinite`.
- A pulse is never stored as firing: `store.setLiteral` writes `.pulse(true)` as off, since `Value` saves every pulse as off and a stored one would fire every frame until the document was reopened. Likewise `LayerRenderer.apply` replaces non-finite geometry before Core Animation sees it; keep new geometry going through `finite`.
- JavaScript patches run on the main thread, limited to `Script.timeLimit` per run by JavaScriptCore's own watchdog (`JSContextGroupSetExecutionTimeLimit`, declared by hand in `Script.swift` because Swift's headers leave it out). A script cut off this way stays off until it is edited.
- `LayerSidebar` rebuilds its list (`.id(…)`) whenever more than one view is added or removed in a single change, and whenever the open view changes. It began as a fix for a SwiftUI `List` with nested `DisclosureGroup`s drawing wrong after several rows arrived at once; the outline is flat now, and the rebuild is kept so a new level always starts clean.
- `ProcessTransport.findNode` asks `zsh -lic` for Node only when there is no controlling terminal. Under a terminal (`papertool assistant`) an interactive shell is stopped for trying to take the terminal, and the run hangs with no output; there the process's own PATH is used.
- A plain view's stored default fill is clear, which is right for a stack and a component's root. `Layer.new(.view)` and `store.addLayer(.view…)` write `Layer.viewFill` so a new view can be seen; a `Layer(kind: .view)` made by hand is invisible until it has a fill.
- A view that clips and also has a shadow clips in an inner layer (`LayerRenderer.contentHost`), because clipping its own layer would cut the shadow off.
- Metal does not pick between `max(float, int)` overloads: shader code needs `max(x, 1.0)`. The agent reference says so; a shader in `ShaderSamples.swift` that breaks this fails `everyShaderInTheGalleryCompiles`.
- `CARenderer` only sees layer changes after `CATransaction.flush()`, and it must share the command queue (`kCARendererMetalCommandQueue`) with the pass that reads its texture. A layer shows a new IOSurface only when given a different one, so `ShaderSurface` alternates between two.
- `papertool examples` gives every patch new ids, so it rewrites every file in `Examples/`. Keep only the ones whose builder changed (`git checkout` the rest).
- A test that uses a `DocumentStore` with an `UndoManager` whose `groupsByEvent` is false must make every edit inside a group, or AppKit stops the test.

- `papertool extension install` and `uninstall` act on the person's real Extensions folder unless given `--extensions <folder>`. In a script, run them only after the build succeeded: an older binary ignores the option.
- An ad hoc build that advertises on the local network (Play on iPhone) may be asked about the network again after a rebuild, as with the keychain below.
- A listener stopped and started again at once on a fixed port fails with "address in use": `DeviceLink.listen` makes its first key without restarting.
- The login keychain ties a key to the signature of the app that saved it, and the app is signed ad hoc: after a rebuild macOS asks before handing a key to the new build. `ExtensionKeys` reads a key once per launch, when a request first needs it.
- The app autosaves in place. Opening a file from `Examples/` and touching it rewrites that file; regenerate with `papertool` afterwards.
- Quit the app before rebuilding (`pkill -x Tango`); a sheet left open blocks a normal quit and you end up testing the old build.
- AppKit can re-deliver a `mouseDown` after its `mouseUp`; the canvas and patch editor guard with `event.timestamp > lastMouseUp`.
- Camera, microphone and location start only when the open prototype needs them, and macOS prompts for access then. `ViewerView.usesDevice` is off for snapshots and tests so they never prompt.
- `xcodegen generate` must be re-run after editing `project.yml` (for example the privacy strings in Info.plist).
- Creating a `ViewerView` makes it the store's `runtime`. For a picture of the prototype use `ViewerSnapshot`, which runs on a store of its own, so the open Viewer keeps feeding live values to the patch graph.
- Patch positions in `Samples.swift`, `Patterns.swift` and `ComponentLibrary.swift` are snapped by the builders. A patch added there without a builder needs `PatchGrid.snap`, or `PatchGridTests` fails.
